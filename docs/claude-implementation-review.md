# tque 実装・ドキュメントレビュー結果

## 1. 総合評価とレビュー範囲

**総合評価**
- high に該当する問題は見つかりませんでした。保存処理は堅実な設計です。具体的には、ロック、一時ファイルからの置換、1世代バックアップ、厳格JSON、CommitUncertain（保存結果不明）の区別がそろっています。エンジン側も、親子と依存の DAG を別々に検査し、深い階層をスタックで処理しています。
- 主な問題は次の4点です。
  - CLI の終了コードが文書の約束（引数エラーは2）と一部食い違う
  - PowerShell ビルドスクリプトが相対パスを想定外の場所に解決する可能性がある
  - TUI と保存結果の扱いに細かい不整合がある
  - テストが一部の挙動を確認できていない。英日ドキュメントにも差分がある
- 公開済みの制約（macOS/ARM64 の実行、署名、Actions の実行が未検証であること）は、追加の具体的な問題がない限り指摘に含めていません。

**範囲と制限**
- 提供されたファイルはすべて読みました。行番号は提供バンドル内の行番号です。
- 次のファイルは提供されていないため、確認していません。
  - `CHANGELOG.md`
  - `docs/detailed-design.md`
  - `third-party-licenses/MODULES.txt`
  - `GO-LICENSE`
  - 各ライセンス原文
- テスト、ビルド、スクリプトはどれも実行していません。cobra、Bubble Tea v2、PowerShell の挙動は私の知識に基づく判断です。
- ソースの出所やライセンス順守を網羅的に証明するものではありません。

## 2. 指摘事項（重大度順）

### C01 — medium — CLI／終了コード
- **場所**: `cmd/root.go:51`, `cmd/root.go:65-68`
- **再現例**: `tque lss` や `tque --tui extra` を実行する。
- **影響**:
  - root コマンドに `Args` が設定されていないため、cobra 標準の引数検査がエラーを返します。
  - このエラーは `usageError` ではないので、`ExitCode` は 1 を返します。
  - 文書（`docs/user-manual.md:238`、`docs/user-manual.ja.md:238`、`README.md:59`）は「引数エラーは2」と約束しており、これを前提にしたスクリプトが誤判定します。
- **根拠**: cobra は `Args == nil` のとき、サブコマンドを持つ root に `unknown command` エラーを返します。そのため `root.go:66-68` の判定には到達しません。
- **対策**:
  - `root.Args` に、引数があれば `usage(...)` を返す関数を設定する。
  - `TestOfflineHelpAndUsage` に `{"lss"}` と `{"--tui","x"}` のケースを追加する。

### C02 — medium — ビルド／Windows（高確度、要確認）
- **場所**: `scripts/build-release.ps1:10`, `scripts/collect-licenses.ps1:5`
- **再現例**: ホームディレクトリで PowerShell を起動し、`Set-Location` でリポジトリへ移動してから、`README.md:17` の `-OutputDirectory ./.work/build` を実行する。
- **影響**:
  - `[IO.Path]::GetFullPath` は、PowerShell の現在位置ではなくプロセスのカレントディレクトリを基準にします。
  - その結果、成果物が別の場所（起動時のディレクトリ配下）に出力され、`README.md:18` の起動行が失敗します。
  - CI は絶対パスを渡しているため影響しません。
- **根拠**: Windows PowerShell 5.1 では `Set-Location` がプロセスのカレントディレクトリを更新しません。pwsh でも同じ挙動が知られていますが、要確認です。
- **対策**: パス解決を `$PSCmdlet.GetUnresolvedProviderPathFromPSPath($OutputDirectory)` に置き換える。

### C03 — low — TUI 操作
- **場所**: `internal/tui/model.go:292-297`
- **再現例**: `e` でタイトルを編集し Enter を押す。保存が終わる前に、`q` を含む文字を続けて入力する。
- **影響**:
  - 保存中は入力モードのままですが、`q` が終了予約として扱われます。
  - 保存が成功すると、アプリが予期せず終了します。
  - ヘルプ（`view.go:253`「入力中のqは文字」）とも、マニュアルとも矛盾します。
- **対策**: 保存中の終了予約は Ctrl+C だけにする。または、`editing()` が偽のときだけ `q` を受け付ける。

### C04 — low — データ検証
- **場所**: `internal/engine/validate.go:109-117`
- **再現例**: `tasks.json` に `"due_date": "+00000001d"` を書く。
- **影響**:
  - この値は10文字なので長さの検査を通り、`Date()` も相対日付として受理します。そのため `Decode` が成功します。
  - 文字列比較では `+` がどの日付よりも前とみなされます。結果として、常に期限超過として扱われ、開始日と期日の前後検査も無意味になります。
  - 「厳格な保存データ検証」という主張に反します。
- **対策**: 保存済みの日付は、`time.Parse(time.DateOnly)` で解析し、元の文字列と一致するかを確認する専用の検査で検証する。

### C05 — low — テストの有効性
- **場所**: `internal/storage/storage_test.go:278-288`, `internal/storage/storage_test.go:89`, `internal/storage/os_windows_test.go:28`
- **問題**:
  - `FuzzDecode` は、`Decode` が内部で `Validate` を呼ぶため、`Decode` 成功時に `Validate` も成功するのは当然です。実質的にはクラッシュ検出しかしていません。C04 も検出できません。
  - `:replace` の障害注入は `replace()` を呼ぶ前に発生します。そのため、実際の置換 API 失敗で `uncertain=true`、つまり CommitUncertain になる経路（`storage.go:260-262`）を確認していません。
  - Windows のテストもエラーの種類（Kind）を確認していません。
  - `:open` の段階はテストされていません。
- **対策**:
  - 置換関数を差し替えられるようにし、置換失敗時に CommitUncertain になること、tmp ファイルが残ることを確認する。
  - fuzz の性質を「独立した検査器との一致」や「再エンコードの往復一致」にする。

### C06 — low — CLI／重複登録のリスク
- **場所**: `internal/storage/storage.go:154-163`, `cmd/root.go:129-132`
- **再現例**: 保存は成功したが、ロック解放（`UnlockFileEx` や Close）が失敗する。
- **影響**:
  - CLI は `Created task #N` を出さず、エラーだけを表示して終了コード1で終わります。
  - スクリプトが再試行すると、`add` が重複登録されます。
  - TUI は `Changed` を見て正しく処理しています（`model.go:238-242`）。
- **対策**: CLI で `res.Changed` が真なら、結果を表示したうえで警告を出す。終了コードは3にするか、文書で明示する。

### C07 — low — 設定
- **場所**: `internal/config/config.go:46-63`
- **再現例**: Unix で `{"data_dir":" /data"}` のように先頭に空白が入る（コピーペーストの誤りなど）。
- **影響**: 空白付きの値が相対パスとして扱われ、`~/.tque/ /data` という意図しない保存先が黙って使われます。「不正な設定は別の場所に切り替えない」という方針に反します。
- **対策**: 前後に空白を含む値は拒否する（`v != strings.TrimSpace(v)` のとき拒否）。

### C08 — low — TUI 表示文言
- **場所**: `internal/tui/model.go:208`, `internal/tui/view.go:171`, `internal/tui/view.go:188-191`
- **問題**:
  - 通常の `r` 再読込でも、「保存結果が不明だった操作は確認を」という通知が毎回出ます。
  - 親なしで追加するモードでも、`(#選択中ID)` と「最新: #選択中…」という無関係なタスクが表示されます。
- **対策**: 保存結果が不明だった場合だけ注意文を付ける。追加モードでは ID と「最新」の行を表示しない。

### C09 — low — 保存の可搬性（未検証の仮説を含む）
- **場所**: `internal/storage/os_unix.go:20-26`, `internal/storage/storage.go:263-268`
- **仮説**: 一部のファイルシステム（WSL の `/mnt/c`、FUSE、9p など）では、ディレクトリの fsync が EINVAL を返す可能性があります。
- **影響**: そうなると、名前変更が成功していても毎回 CommitUncertain（終了コード3）になり、TUI は保存結果不明の状態で止まります。
- **補足（設計どおりの挙動に対する推奨）**: Windows の共有違反のように明確な置換失敗も CommitUncertain にするのは文書どおりの設計です。ただし、ウイルス対策ソフトなどの一時的なファイル保持で頻発しないか、実際の環境で確認することを推奨します。

### C10 — low — 読み取りに書き込み権限が必要
- **場所**: `internal/storage/storage.go:90`, `internal/storage/storage.go:130`
- **問題**: `Read` も `lock` ファイルを `O_RDWR|O_CREATE` で開きます。そのため、読み取り専用のディレクトリや退避したコピーに対して `ls` を実行すると StorageFailure になります。
- **文書との関係**: `README.md:100` の「Reads do not create tasks.json」は正しいですが、`lock` が作られることと書き込み権限が必要なことが書かれていません。
- **対策**: 文書に明記する。または、ロックを取れない場合に警告付きで読み取る。

### C11 — low — インストーラー
- **場所**: `installer/tque.iss:22`
- **問題**: `MinVersion=10.0.22000` は Windows 11 以上を意味します。そのため Windows 10 にはインストールできませんが、README とマニュアルに記載がありません。
- **対策**: 意図した制限かを決めたうえで、文書に明記するか、テストしてから下限を下げる。

### C12 — low — スクリプトの使い勝手
- **場所**: `scripts/package-zip.sh:17`, `scripts/build-release.sh:4-7`, `scripts/package-zip.sh:4-7`, `scripts/collect-licenses.sh:4-7`
- **問題**:
  - `zip` が見つからないとき、何も表示せずに終了コード1で終わります。
  - 引数で受け取る相対パスは、`cd "$repo"` の後で解決されるため、呼び出し元ではなくリポジトリを基準にします。README の例はリポジトリ直下で実行するので問題ありませんが、別の場所から実行すると意図しない場所に出力されます。
- **対策**: `cd` の前に出力先を絶対パスにする。`zip` がない場合は明示的なエラーメッセージを出す。
