## 1. 目的と適用範囲

タイトル、親子関係、依存関係、開始日、期日、進捗を管理するGo製の単一バイナリを設計する。CLIとTUIは同じ業務ロジックと保存処理を使用する。本文、クラウド同期、複数ユーザー共有、通知、繰り返しタスクは今回の基本設計の対象に含まれない。

本書の「確定」は基本設計または利用者の作業ルールを根拠とする。「提案」は設計者による案であり、利用者の承認を意味しない。未決事項は第2章に集約する。外部ライブラリの具体的API、採用バージョン、OS固有の保証は未検証であり、実装前に一次資料と実機で確認する。

本書の追加・具体化した動作は、第2章の提案に属する。断定形の記述も、提案を採用した場合の動作定義であり承認済みという意味ではない。[レビュー対象の第1版](detailed-design-reviewed-v1.md)、[レビュー原文](claude-review.md)、[指摘への評価と対応](review-response.md)を別途保持する。

今回の成果物は設計書とClaude Codeのレビュー記録。アプリ実装、依存取得、ビルド、パッケージ作成、Git操作は行わない。

## 3. 構成と責務

| パッケージ | 責務 | 禁止する依存 |
| --- | --- | --- |
| `internal/model` | 永続データ、状態定数、要求・結果の型 | CLI、TUI、ファイルI/O |
| `internal/engine` | 入力検証、タスク操作、DAG検査、日付、表示値計算 | Cobra、Bubble Tea |
| `internal/storage` | ロック、読込、保存、スキーマ検証の入口 | CLI/TUI表示 |
| `cmd` | Cobraの引数処理、engine呼出、出力、終了コード | 独自の業務ルール |
| `internal/tui` | Bubble Teaによる入力状態と描画、engine呼出 | 独自の保存処理 |
| `main.go` | コマンド起動とプロセス終了 | 業務ロジック |

engine内のServiceがRepositoryインターフェースを使用し、storageが実装する。グラフ・進捗計算は副作用のない関数に分離する。時刻はClockとして注入し、日付のテストを再現可能にする。

概念上のインターフェース（採用ライブラリのAPIではない）:

```go
type Repository interface {
    Read(ctx context.Context) (Document, error)
    Update(ctx context.Context, expectedRevision *uint64,
        mutate func(*Document) error) (Document, error)
}
```

Updateは排他ロック取得、最新データ読込、revision照合、複製データへの変更、全体検証、保存、ロック解放を一つの処理として扱う。mutate失敗時は元データもファイルも変更しない。ロック中に対話入力や描画を待たない。

## 4. データモデル

### 4.1 保存ドキュメント（Q01/Q02/Q12の提案）

```json
{
  "schema_version": 1,
  "revision": 1,
  "next_id": 2,
  "tasks": [
    {
      "id": 1,
      "title": "全体設計",
      "status": "todo",
      "progress": 0,
      "progress_mode": "auto",
      "created_at": "2026-10-21T00:00:00Z"
    }
  ]
}
```

未作成時の論理状態はschema_version=1、revision=0、next_id=1、tasks=[]。読取だけではtasks.jsonを作成しない。既存のデータディレクトリ内では読込時もlockファイルの作成を許可する（第6.1節）。IDは正のint64整数、next_idもint64とし既存最大IDより大きい。next_idを増加できない追加操作とrevisionの上限を超える更新はエラーにし、桁あふれで再利用しない。

Taskは基本設計の各フィールドを保持し、progress_modeを追加する。日付は時刻なしのYYYY-MM-DD、作成・完了日時はUTCのRFC3339文字列。未設定の親、日付、完了日時は省略する。依存IDは重複除去し昇順で保存する。

保存時のprogressは数値指定またはdone操作で設定する値であり、親の集計値とは区別する。集計値は保存せず、表示用TaskViewのeffective_progressに計算する。モード切替や子の追加・削除では保存進捗を書き換えない。最後の子がなくなったタスクは、保持していた保存進捗を表示する。done→undoneの後なら100となる。詳細は第4.3節を唯一の状態定義とする。

### 4.2 不変条件

- IDの重複、存在しない親・依存先、自己参照、循環を拒否する。
- statusはtodoまたはdone。progressは0〜100。doneなら保存progress=100、completed_atあり。todoならcompleted_atなし。
- progress_modeはautoまたはmanual。葉は保存progressを表示し、親のautoだけが集計対象。
- created_atは編集で変更しない。doneの再実行は成功扱いとし完了日時を変更しない。
- start_dateとdue_dateが両方あればstart_date <= due_dateとする提案。
- 不正な保存データを空データ扱いしない。未知のスキーマや未知フィールドを読み捨てて上書きしない。

既存の実装・旧データ形式は確認されていないため、自動移行は設計しない。将来の形式変更では別途移行手順とバックアップを設ける。

### 4.3 進捗・状態の組合せ（Q02/Q03/Q06/Q07の提案）

| status | 子の有無 | mode | 保存progress | effective_progress |
| --- | --- | --- | --- | --- |
| todo | なし | auto/manual | 0〜100を保持 | 保存progress |
| todo | あり | manual | 0〜100を保持 | 保存progress |
| todo | あり | auto | 0〜100を保持（集計には不使用） | 直下の子のeffective_progress平均を切り捨て |
| done | なし/あり | auto/manual | 必ず100 | 必ず100 |

| 操作 | 保存progress | mode | status・完了日時 |
| --- | --- | --- | --- |
| add（-p省略またはauto） | 0 | auto | todo・日時なし |
| add -p N | N | manual | todo・日時なし |
| edit -p N | N。doneでN<100なら拒否 | manual | 変更しない |
| edit -p auto | 保持 | auto | 変更しない |
| done | 100 | 保持 | done・初回のみ完了日時設定 |
| undone | 保持 | 保持 | todo・完了日時削除。既にtodoなら無変更成功 |
| 子の追加・削除・移動 | 保持 | 保持 | 変更しない |

葉のauto指定も許可し、保存値を失わず将来親になった場合の集計方法を選択できる。数値指定済みの葉に子を追加するとmanualは維持される。これは自動集計の不具合ではなく固定継続の提案仕様であり、CLI/TUIの行に`[manual]`を表示して明示する。自動集計への変更は-p autoまたはTUIのpから行う。完了前の進捗を履歴として復元する機能は持たない。

## 5. 入力と業務ロジック

### 5.1 入力規則（Q11の提案）

- titleは前後の空白を除去し、空文字、改行、タブ、ESC等の制御文字を拒否する。日本語・絵文字を保持する。表示時にも端末制御シーケンスを出力しない。
- IDは正の10進整数。0、負数、小数、範囲外を拒否する。
- 日付は厳密なYYYY-MM-DD、today、+Nd（Nは0以上の整数）。ローカル日付を操作受付時に一度取得し、暦日加算する。無効日とオーバーフローを拒否する。日付は着手の強制制限に使わない。
- editの未指定は維持、noneはparent/dep/start/dueの解除。titleの文字列noneは通常のタイトル。progress解除はQ02のautoを用いる。
- --depはカンマ区切りと繰返し指定を受け付け、editでは集合全体の置換。例: `--dep 2,3 --dep 4`。noneとIDの併用は拒否する。基本設計の`<id...>`はこの構文に具体化する提案。
- editで変更フラグがない場合は使用方法エラー。複数フラグの更新は全件成功または全件失敗とする。

### 5.2 操作

| 操作 | 更新内容 | 主な検証 |
| --- | --- | --- |
| Add | next_idを割当、todo、作成日時設定、next_id増加 | タイトル、日付、親、依存、進捗 |
| Edit | 指定された属性だけ置換 | 変更後のドキュメント全体 |
| Done | status=done、progress=100、完了日時設定 | 存在、Q04の方針 |
| Undone | status=todo、完了日時削除 | Q06の方針 |
| Remove | 対象または子孫集合を削除 | cascade指定、集合外からの依存参照 |

Addで-pを指定した場合はmanual、省略時はautoとする提案。-p 100だけではdoneにしない。doneのタスクへの100未満の進捗指定は拒否し、先にundoneを要求する。親や依存関係、タイトル、日付はdoneでも変更できる案とする。

自動進捗はdoneを100として優先し、todoのmanualは保存値、todoのautoで子ありは直下の子のeffective_progress平均の切り捨て、葉は保存値とする。子変更後は祖先を再計算する。親statusの自動変更は行わない。

blockedは依存先に一つでもtodoがあるとき成立する（Q14の提案）。依存先なしの場合はfalse。blocked_byには未完了依存IDのみを昇順で列挙し、親や開始日からは推論しない。自分のstatusがdoneでも同じ判定を使い、CLI/TUIとも`(blocked by #2, #3)`を表示する。JSONも同じblocked/blocked_byを返す。--blockedは一覧のstatusフィルタを適用した後、この判定で絞り込む。新たなactionable_blockedフィールドは追加しない。

### 5.3 グラフ

ID→TaskとParentID→子ID列を構築する。参照存在を確認後、白・灰・黒の訪問状態によるDFSで閉路と経路を検出する。親子は子→親の包含関係、依存はタスク→先行必須タスクとして、別々に検査する案とする。エラーには`#1 -(parent)-> #3 -(parent)-> #1`または`#1 -(dep)-> #3 -(dep)-> #1`のように関係種別を付ける。

| 例 | Q08案での扱い |
| --- | --- |
| 親が子に依存 | 許可。子の完了まで親にblocked警告 |
| 子が親に依存 | 許可。親の完了まで子にblocked警告。親の完了は子から独立 |
| 兄弟間・別の枝の子孫間の依存 | 依存グラフが非循環なら許可 |
| 親と子が互いに依存 | 依存グラフの閉路として拒否 |
| 親子グラフ単独では非循環、依存グラフ単独でも非循環だが結合時のみ循環 | 拒否しない。包含を先行条件として扱わないため |

深い階層でも処理可能なよう、実装は明示スタックを用いる。検査・進捗計算はO(V+E)、順序確定のソートはO(V log V)を目安とする。削除集合は親子だけを辿り、依存先を巻き込んで削除しない。

## 6. ストレージと並行実行

保存先は基本設計どおり`~/.tque/tasks.json`。ホーム解決失敗はエラーとする。テストは一時ディレクトリを注入し、実ユーザーデータを使わない。

### 6.1 排他処理案

`~/.tque/lock`を対象にOSのファイルロックを使用する方式を提案する。ファイルの存在そのものをロックとせず、異常終了後に手動削除を要求しない方式を選ぶ。ロックファイルは解放時に削除しない。Windows/Unixの実装または採用ライブラリは未選定。ネットワーク共有上の利用保証は対象外とする案。

読込・更新とも同じ排他ロックを使用する案とする。共有ロックは初期版に導入しない。読込では、データディレクトリが存在しないことを確認した場合にその時点の空状態を返す。後続の作成操作より前の読込として扱い、その後の更新は必ずロック下で再読込する。存在確認時の権限エラー等を「存在しない」と解釈しない。

ディレクトリが存在する場合はlockを必要に応じて作成し、排他ロック取得後にtasks.jsonを調べる。本体が未作成なら空状態を返すが、本体は作成しない。更新時のみデータディレクトリを作成する。ロック取得に失敗した読込は、ロックなしで処理を続行しない。

待機はcontextで中断可能にし、提案値5秒でタイムアウトを返す。OSの非ブロッキング取得と中断可能な待機を組み合わせる方式を候補とし、呼出しの契約と再試行間隔は技術検証後に確定する。全プロセスが同じロック規約に従うことを前提とし、外部エディタや同期ソフトによる書換えは保護できない。初期版の保証対象はローカル保存とし、保存先変更用の公開フラグ・環境変数は追加しない。

### 6.2 更新手順

1. ロックを取得し、最新JSONを読んで形式・不変条件を検証する。
2. expectedRevision指定時は一致確認。不一致なら変更せず競合エラー。
3. ドキュメントを複製し、変更と全体検証を行う。
4. 実変更があればrevisionを1増加。無変更なら保存しない。
5. 同じディレクトリの`tasks.json.tmp`へ完全なJSONを書き、Sync、Closeを行う。
6. OS別の置換処理でtasks.jsonを置換する。
7. 必要な永続化処理を行い、結果を返してロックを解放する。

固定tmp名はロック所有者だけが操作する。候補データの検証とJSON生成を完了してから、tmpを作成または切り詰めて全量を書き込む。残留tmpは自動復元に使わない。本体が破損している場合はtmpにも触れず停止する。書込・Sync・Close失敗後は置換を行わず、tmpの削除を試みる。削除失敗は副次エラーとして通知し、本来のエラーを保持する。置換結果が不明ならtmpも自動削除せず、再読込と確認に回す。本体を削除してからリネームする方式は使用しない。

初期案では置換を自動再試行せず、失敗を返す。再試行を追加する場合は「本体が未変更と判定できる一時的エラー」をOS別に特定し、回数・待機上限・中断処理を定めてから導入する。未検証のエラーを一括で再試行しない。

基本設計はos.Renameによるアトミック置換を要求しているが、全対象OSでの上書き・アトミック性・電源断耐性は未検証。Windowsを含むOSごとのAPI契約を確認し、必要なら専用実装に置き換える。原子的な可視性と電源断後の永続性は別の受入項目とする。

置換前の失敗、または置換APIの契約上本体が未変更と確認できる失敗はStorageFailureとする。置換の成否自体を判別できない場合と置換後の永続化確認失敗はCommitUncertainとし、Addを自動再試行しない。ロック解放失敗は保存の成否とは別に通知する。壊れたJSONは元ファイルを保持して停止し、初期化・切捨てをしない。

| OS別の技術確認項目 | 現在の状態 | 完了条件 |
| --- | --- | --- |
| 初回作成と既存ファイル置換のAPI | 未選定・未検証 | 一次資料、採用API、失敗時の本体状態を記録 |
| 可視性と永続化の保証範囲 | 未検証 | Sync/Close/置換後処理と各保証の範囲を記録。電源断耐性を推定で保証しない |
| 排他ロック・中断・異常終了後の解放 | 未検証 | 複数プロセスと異常終了による試験結果を記録 |
| 制限付きハンドル・読取専用属性・残留tmp | 未検証 | データ消失なし、失敗段階と通知を実機確認 |

この表の未完了項目を「Windows対応確認済み」と扱わない。技術検証用の小規模実装は、製品仕様確定と区別して進められる。

### 6.3 TUIとCLIの同時利用

TUIは一覧のrevisionと編集開始時のrevisionを保持する。保存は最新データに対し要求を適用するが、revisionが異なる場合は拒否する。再読込後も入力案を保持して利用者に再操作を求める。無関係なタスクの変更でも競合になる保守的な設計とする。

追加提案としてrキーで再読込する。初期版では常時監視を行わず、起動時・操作成功時・競合時・明示再読込時に表示を更新する。

## 7. CLI詳細

基本設計のadd/edit/done/undone/rm/lsを実装対象とする。引数なしまたは--tuiでTUIを起動し、サブコマンドと--tuiの併用は拒否する提案。TUI起動時に対話端末がなければ明確なエラーを返す。

| 項目 | 提案仕様 |
| --- | --- |
| 正常出力 | stdoutへ結果。失敗説明はstderr |
| 終了コード | 0成功、1業務・保存・競合エラー、2引数エラー、3保存結果不明（CommitUncertain） |
| ls | Q09の対象をID昇順で表示 |
| --tree | 親子順で表示。フィルタ対象の祖先を文脈行として残し、対象外であることを表示 |
| --blocked | todoかつblocked。--all併用時はdoneの関係上の警告も対象 |
| --json | 表示用の行をJSON配列で出力。色と通常メッセージを混ぜない |
| --tree --json | 拒否する提案。階層はparent_idから復元可能 |
| 空一覧 | 通常表示は対象なし、JSONは[]、終了コード0 |
| --help/--version | 保存領域へアクセスせず出力 |

JSON行はTaskの各属性とeffective_progress、blocked、blocked_byを持ち、保存ドキュメントとは別の公開形式とする。--jsonでは文脈用祖先を混入しない。フラグの正当性は保存処理を呼ぶ前に確認する。

### 7.1 入力と出力の契約

| 入力 | add | edit |
| --- | --- | --- |
| -p 0〜100 / auto | 第4.3節の初期値を設定 | 第4.3節の遷移 |
| --parent/--dep/--start/--due none | 拒否。未設定なら省略 | 該当属性を解除 |
| titleとしてnone | 通常のタイトル | 通常のタイトル |
| 未指定の属性 | 初期値（関係・日付なし） | 保持 |

日付表示は年を含むYYYY-MM-DDに統一し、保存値と同じ意味にする。通常一覧は`ID [ ]/[x] TITLE [manual] [########.. 80%] START -> DUE (blocked by #N)`の要素順とする。manual以外はモード表示を省略、進捗バーは10桁で塗る数をeffective_progress/10の切捨て、空きは`.`とする。日付なしなら日付欄を省略、片側だけなら`START ->`または`-> DUE`。依存警告なしなら末尾を省略する。ツリーはIDの前に枝を付け、文脈用祖先には`[context]`を付ける。階層内の兄弟もID昇順。

追加は`[+] Created task #ID: TITLE`、編集は`[*] Updated task #ID`、完了は`[x] Completed task #ID`、未完了へ戻す操作は`[ ] Reopened task #ID`、削除は`[-] Removed N task(s): #ID, ...`。無変更成功は`[=] Unchanged task #ID`とし、revisionは増加させない。エラーはstderrに型名・対象・理由を表示する。

CLI出力はUTF-8、初期版は色なしとする。TUIは色と文字を併用するが、NO_COLORが非空なら色を無効化する。古いコードページのコンソールへの自動変換はしない。Windows実端末での表示確認を別途行う。

| JSON属性 | 型・未設定時の規則 |
| --- | --- |
| id | 正のint64範囲のJSON整数 |
| title / status / progress_mode | 文字列。statusとmodeは定義済みの列挙値 |
| progress / effective_progress | 0〜100の整数 |
| parent_id | 整数。未設定なら省略 |
| depends_on / blocked_by | 昇順・重複なし整数配列。空でも[]を出力 |
| start_date / due_date | YYYY-MM-DD。未設定なら省略 |
| created_at / completed_at | UTCのRFC3339。completed_atはtodoなら省略 |
| blocked | boolean。第5.2節の判定 |

nullは出力しない。JSON配列内のタスクはID昇順。保存側の省略可能なdepends_onとは出力規則を区別する。整数の精度を保てるJSON処理系を前提とし、CLIがIDを浮動小数点数へ変換しない。

## 8. TUI詳細

一覧、テキスト入力、削除確認、保存中、エラー表示を状態として扱う。選択は行番号ではなくタスクIDで保持し、削除時は近傍行へ移す。ウィンドウサイズ変更時は表示幅とスクロール範囲を再計算する。

| 操作 | 状態遷移と処理 |
| --- | --- |
| j/k・上下 | 一覧の選択移動。末尾と先頭で停止 |
| Space | 対象のdone/undone要求 |
| +/- | 表示進捗±10を0〜100へ制限してmanual指定。doneの減算は先にundoneを促す |
| a/A | タイトル入力。Aは選択タスクを親として保持 |
| e | 現在タイトルを初期値に編集 |
| s/d | 現在日付を初期値に入力。空欄で解除 |
| l | 現在の依存ID列を初期値に入力。空欄で解除 |
| x/Delete | 対象と削除件数を表示。子ありなら子孫削除を明示して確認 |
| Enter/Esc | 入力確定・取消。取消時は保存しない |
| q/Ctrl+C | 一覧では終了。入力中のqは文字、Ctrl+Cは未確定入力を破棄して終了 |
| r（追加提案） | 一覧を再読込 |
| p（追加提案） | 進捗入力。0〜100またはautoを指定 |

削除確認は既定を取消とし、明示的な肯定入力だけで実行する。子孫集合外からの依存があればQ05に従って拒否し、参照元IDを表示する。

確定操作ごとに保存し、成功後に表示を更新する。終了時の全件上書きはしない。保存中は二重更新を受け付けず、終了要求は保存結果が判明してから処理する。入出力はBubble Teaの非同期コマンドから行い、結果メッセージで状態を更新する。

日本語・結合文字・絵文字はバイト数で切らず、端末表示幅を考慮する。幅不足ではタイトルを省略し、極小画面ではサイズ不足表示を行う。blockedは色だけでなく文字でも示す。入力中のj/k等は編集文字として扱う。エラー後も入力を保持して修正できるようにする。

### 8.1 状態遷移の補足

- Space、+/-はキー受付時の一覧revisionを送る。入力欄と削除確認は開始時のrevisionを保持する。
- 保存中は「保存中」を表示し、追加の更新キーは破棄して後から再生しない。リサイズは処理し、終了要求は保留する。
- 保存成功後は返却されたDocumentで一覧を更新する。表示再読込の失敗を、保存失敗と混同しない。
- 競合時は再読込し、入力案を表示して再確定を求める。新しいrevisionで自動再送しない。対象が消えていれば編集を中止し、入力案を通知欄に残す。
- 保存中の終了要求は成功後に終了する。失敗・結果不明の場合は終了保留を解除し、エラーを表示して利用者の再操作を待つ。
- 追加成功時は新タスクを選択して表示位置を合わせる。削除後は旧行位置に来た次の行、なければ前の行を選択する。空一覧では選択なし。
- 選択なしで対象を必要とするキーは「対象タスクがありません」と通知する。a、r、qは使用できる。
- 親の変更は初期版ではCLIのedit --parentで行う。TUIに新たな親変更キーは追加しない。
- 削除確認は`y`で確定、`n`/Esc/Enterで取消。確認中のqは取消、Ctrl+Cは未確定の削除を破棄して終了する。
- TUIの日付・モード・進捗・警告の意味と書式は第7.1節に合わせる。pの初期値はautoならauto、manualなら保存進捗とする。

## 9. エラー設計

engine/storageからは型付きエラーを返し、UIが表示する。例: InvalidInput、NotFound、CycleDetected、ReferencedTask、RevisionConflict、LockTimeout、CorruptData、UnsupportedSchema、StorageFailure、CommitUncertain。

エラーには操作、対象ID、原因となる参照ID等を含める。成功と確認できない保存を成功表示しない。保存エラー時の次操作は再読込を基本とする。無限リトライや破損データの自動修復は行わない。

JSON構文エラーと不変条件違反はCorruptDataの理由で区別し、検出箇所・対象IDを示す。未知のスキーマはUnsupportedSchemaとする。これらではlsを含むデータ操作を停止し、壊れたデータ用の一覧・修復コマンドは初期版に追加しない。help/versionは利用できる。

手動復旧は、(1)利用者がtqueを終了、(2)tasks.jsonと残留tmpを別名で退避、(3)既知の正常なバックアップを復元、または退避コピーを基に指摘された不整合を修正、(4)lsで再検証、の順とする。未知のスキーマ番号を書き換えて読み込ませない。next_idは削除済みIDの履歴を含むため、max(ID)+1へ無条件に縮めない。履歴が不明なら採番非再利用を保証できないことを明示する。アプリが自動でファイルを削除・初期化することはない。

ロック解放等の副次エラーはCLIではstderr、TUIでは通知欄へ出す。保存完了が確認できている場合は「保存済み・ロック解放失敗」と明示し、未保存と誤認させない。CLIは終了コード1を返すが自動再試行を促さない。永続ログファイルは初期版に設けない。
