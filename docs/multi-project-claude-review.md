## 総合評価

デフォルトProjectID、ProjectIDと表示名の分離、schema 3を読み込み時に書き換えない方針は現行実装に合う。一方、全体一意IDとプロジェクト単位の操作範囲、移行バックアップ、既存タスクの分類変更手段、厳格JSONの新フィールド定義が未解決であり、現案のまま詳細設計へ反映するのは危険。

## 重大度: 高

### H1: 全体一意IDとプロジェクト単位操作・renumberの衝突

現行renumberは単一ID空間で番号間の全タスクを移動させる。プロジェクト画面からデフォルトのタスクIDを振り直すと、非表示プロジェクトのID・参照まで変わる。TUI操作境界と矛盾し、別TUIの編集中断も起こり得る。

**修正案:** ID空間を先に決定する。全体一意を維持するなら、他プロジェクトへ影響するrenumberを拒否または明示確認する。プロジェクト別IDを採用するなら、CLI IDをプロジェクト内で解釈する。

### H2: 全体採番がデフォルトの既存表示を変える

現行採番は全タスクの最大ID+1、TUI列幅も全体最大IDに基づく。名前付きプロジェクトでIDが大きくなると、デフォルト側にIDの飛びと列幅変化が出る。

**修正案:** プロジェクト別ID空間を採るか、全体IDを受け入れる条件をデフォルト動作に明記する。

### H3: schema移行バックアップとschema 2経路が不足

1世代の通常バックアップは次回保存で上書きされ、旧版がschema 4を読めないため安全なダウングレードを保証しない。schema 2→3の既存移行専用バックアップとの整合も不足。schema 2の直接移行、旧版TUIの扱い、バックアップ同名時の手順も未定義。

**修正案:** `tasks.schema3.backup`等の移行専用バックアップ、同名・異内容時の停止手順、schema 2対応方針、旧版復旧手順を定義する。

### H4: 既存タスクをプロジェクトへ移せない

既存タスクを全部デフォルトへ入れ、移動手段を提供しないと、分類し直すにはID・履歴を失う再作成しかない。

**修正案:** ルートと全子孫の一括移動を提供する／既存タスクは移せないと受容する／一回限りの移行コマンドを提供する、から選ぶ。

### H5: 一覧スコープと互換性が不明

CLIの`ls --all --json`も全プロジェクトかデフォルトだけか不明。変更がないまま結果だけ部分化すると既存スクリプトが静かに欠落データを受け取る。スコープ外IDのエラーも不明。

**修正案:** `--all-projects`等の全件取得手段、JSONのProject識別フィールド、他プロジェクトIDを指定した場合のエラーを定義する。

### H6: 厳格JSONに必要なProjectフィールドと検証規則が不足

現行storageは未知フィールドを拒否する。ProjectのID/name、task.project_idの必須性、既定ProjectID・表示名、名前規則、衝突判定方式、検証エラー条件が曖昧だと全読み取り操作が停止し得る。

**修正案:** フィールド・型・必須性・既定値・名前照合を固定し、欠落や重複などのCorruptData条件を列挙する。

## 重大度: 中

- **M1 アーカイブ定義不足:** アーカイブ済みの編集可否、名前再利用、復元、TUI選択、操作後の画面遷移が未定義。読み取り専用にしてエンジンで拒否する案。
- **M2 名前解決の競合:** 名前→ProjectID解決を更新ロック外で行うと、rename/create競合で意図しないプロジェクトへ追加される。Updateのmutate内で解決し、TUIはProjectID保持を推奨。
- **M3 TUI状態遷移不足:** 保存中・結果不明・入力中の`P`、切替時のsort/filter、ヘッダー幅、再読込後にプロジェクトが消えた場合が未記載。
- **M4 CLIフラグ境界不足:** `--project`とTUI起動、project管理サブコマンド、空指定、help/version/completionのデータ未読込契約が未定義。
- **M5 詳細設計と現行実装の差:** `undone`後進捗、親タスク完了の子制約、sort名、TUIキー等に不一致がある。設計更新時は実装・現行詳細設計・本案の基準を整理する必要がある。

## 重大度: 低

- CLIの成功表示、JSON出力、`project list`の書式・終了コードの互換性。
- 補完時にデータを読まない現行方針とプロジェクト名補完の関係。
- プロジェクトごとの折り畳み保持と選択行のリセット条件。
- schema 4を旧版が読めないこと、移行バックアップ衝突、名前解決競合を検証項目へ加える。

## 利用者判断を要する事項としての提示

1. IDを全体一意のままにするか、プロジェクト内IDにするか。レビュー推奨は後者だが、永続形式と出力契約への影響が大きい。
2. CLIの全プロジェクト一覧を提供するか。提供するなら専用の明示フラグとProject識別子が必要。
3. 既存タスクを移す操作を初版へ含めるか。レビュー推奨はルートと全子孫の一括移動。
4. アーカイブの挙動、schema 2対応、`--project`指定でTUIを開く挙動。
