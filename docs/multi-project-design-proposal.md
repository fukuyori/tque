# 複数プロジェクト対応の設計案

状態: 提案。詳細設計への反映・実装は未承認。
作成日: 2026-10-24

利用者確認済み: 選択したタスクの子孫も一括移動の対象に含める（2026-10-24）。

## 1. 目的と前提

現在のtqueは1つの保存ドキュメント内の全タスクをTUIに表示する。ルートタスクごとの空行はあるが、プロジェクトの境界はない。このため、複数プロジェクトのタスクが一つの一覧に並び、プロジェクトごとに選んで管理できない。

目的は、複数プロジェクトのタスクを同じtqueデータ保存先で管理し、TUIとCLIで対象プロジェクトを選べるようにすること。既存の操作性を維持し、プロジェクトを意識しない従来操作を変えない。

## 2. 参考リポジトリから得た方針

- [PM (pbower/project_management)](https://github.com/pbower/project_management) はタスクに project 属性を付け、一覧等で `--project` フィルタを使う構成をREADMEで説明している。tqueではこの明示的な対象指定を参考にする。一方、PMのプロジェクトはタスクの分類属性であり、tqueで必要な「選択したプロジェクトだけを操作する境界」と同じ設計ではない。
- [RonDO](https://github.com/roniel-rhack/rondo) はタスク等を単一のローカルSQLiteデータベースに保存する。単一保存領域の考え方は参考になるが、今回確認したREADMEには複数プロジェクトの切替仕様はない。
- [rusk](https://github.com/tagirov/rusk) は複数形式・場所のデータベースと保存前バックアップ等を説明している。tqueには既に保存先設定・原子的保存・バックアップがあるため、データソース選択方式は採用せず、現行tasks.jsonにプロジェクト境界を加える案とする。

参照したのは各リポジトリの公開READMEであり、実装ソース全体の同等性や、そこに記載のない挙動は確認していない。

## 3. 既定動作

- 既存タスクを「デフォルト」プロジェクトに所属させる。
- プロジェクトを明示しないCLI操作はデフォルトプロジェクトを対象とする。既存タスクはデフォルトに残るため既存データのIDと表示は保たれるが、名前付きプロジェクトを作成した後は明示スコープが必要になる。
- TUI起動時はデフォルトプロジェクトを表示する。`--project <名前>`を指定した場合はそのプロジェクトを開く。指定は起動ごとのもので、設定には保存しない。
- TUIの`P`選択は起動中のみ有効とする。次回起動で別プロジェクトを暗黙に開かない。
- TUIは常に一つのプロジェクトだけを表示する。全プロジェクトを混在させたCLI一覧は`--all-projects`で明示した場合に限る。

## 4. TUIでの操作設計

- TUIを主要なプロジェクト管理画面とし、プロジェクトの選択・作成・改名とタスクツリーの移動をTUI内で完結できるようにする。
- 通常の一覧画面ではヘッダーに選択中プロジェクト名を常時表示する。起動直後はデフォルトプロジェクトを開き、TUI内の選択状態は起動中のみ保持する。
- `P`で専用のプロジェクト画面を開く。画面にはプロジェクト名と未完了・完了を含むタスク数を表示する。上下で選択、Enterで切替、Escで元の一覧へ戻る。デフォルトは固定項目として常に先頭に置く。
- プロジェクト画面では`a`で作成、`e`で名前変更を行う。デフォルトの名前変更は拒否する。削除・アーカイブは初版に含めない。
- 一覧画面で`v`を押すとカーソル行に一括操作用の印を付ける／外す。印は表示IDではなくInternalIDで保持する。選択数を選択中のフッターに表示し、`V`は確認後に全印を解除する。Spaceは既存どおり完了切替に使う。
- `M`で選択した複数タスクを別プロジェクトへまとめて移す。選択が0件なら通知して何もしない。印は一つの移動元プロジェクト内に限る。印が残っている間は`P`による切替を拒否し、移動または選択解除を促す。
- 検索・フィルタ・折り畳みを変えても選択印は保持する。印はInternalIDで識別し、再読込で現在のProjectに存在しないIDは解除して件数を通知する。折り畳み・カーソル位置もProjectIDとInternalIDで管理する。画面外へスクロールしただけの印は非表示件数に含めず、検索・フィルタ・折り畳みで隠れた印は数に含める。印を付けた行は`*`、選択枝に含まれて自動的に移動する子孫行は`+`で示す。折り畳み行の下に選択印が隠れている場合は行上に件数を示す。行の先頭2セル（カーソル表示領域）を使い、通常列幅を増やさない。フッターは選択中専用の短いキー案内と件数表示に切り替える。
- `M`を押した時点で、選択枝の外へ出る親子関係と依存関係を検査する。親子関係は選択枝の根の親だけを解除対象として許可し、それ以外の境界関係は移動先選択へ進む前にタスク名・IDを示して拒否する。依存の状態（未完了・完了）は問わず、境界をまたぐものはすべて拒否する。
- 移動先一覧には作成済みの他プロジェクトだけを表示する。まだ名前付きプロジェクトがない場合や新規作成したい場合は`a`で作成し、作成後にそのProjectを移動先として選べる。Project作成はタスク移動と別の保存操作で、作成だけが完了して移動を中止した場合は空Projectが残ることを明示する。schema移行が伴った場合は、旧版で読めない形式へ更新したこととバックアップ先を通知する。移動元自身は候補に含めない。
- 確認画面の冒頭に、移動元・移動先、手動選択件数、枝数、移動対象総数、非表示対象数、切り離される親、移動元親の自動進捗が変わる場合は変更前後の値、ID再割当ての有無、移動し戻しても元IDへ戻らないことを要約する。最小端末40x10で要約を優先し、明細は下に続けてスクロールできる。末尾まで読むことは確定条件にしない。本文には全タスクの移動前ID→移動後IDを示す。`y`で確定、Esc/n/q/Enterで中止する。
- 選択タスク同士が祖先・子孫なら、祖先側を移動単位としてまとめ、同じ子孫を二重に数えない。親子関係をまたがない選択枝はそれぞれ移動後のルートとなり、枝内部の階層は保つ。
- 確認開始時のrevisionを保存要求に含める。競合した場合は自動再送せず一覧を再読込し、InternalIDで残っている印を保つ。移動集合と関係チェックが変わった可能性があるため、選択を再確認するよう通知する。依存・親子関係の検査は更新ロック内でも再実行する。
- 通常の保存失敗では一覧へ戻り、印を維持する。保存結果不明では追加操作を止め、再読込して印のInternalIDが移動元・移動先・どちらにもない状態の件数を集計表示してから印を解除する。結果不明の移動は自動再送しない。
- 成功後は移動元プロジェクトに留まり、検索とフィルタを維持する。移動された印を解除し、移動前の位置に近い次の行（なければ前の行）を選択する。通知に移動件数・移動先を示す。移動先へは利用者が`P`で切り替える。
- 選択プロジェクトのタスクだけを一覧・検索・集計し、追加・編集・完了・削除・ID振り直しも選択中に限定する。
- プロジェクト切替時は検索とフィルタを解除し、並び順を維持する。選択行とスクロール位置は新しいプロジェクトの先頭へ戻す。折り畳み状態はプロジェクトごとに保持する。
- 保存中、保存結果不明、編集・削除等の入力中はプロジェクト切替・一括移動を受け付けない。入力モード中の`P`は文字入力として扱う。空一覧・一致なしでも`P`、`M`、`V`は通知を出して動作する。一覧の大文字キーは既存`J`/`K`と同様のキー表記差を受け付ける。
- ヘルプには、一覧画面・プロジェクト画面・移動確認の状態ごとに使えるキーを表示する。プロジェクト切替後の選択位置を画面上部で確認できるようにする。

現在の一覧キー割当では`P`、`v`、`V`、`M`は未使用。画面状態ごとのキー表に追加し、既存モードと衝突しないことを受入条件にする。`V`の全解除には、印が1件だけでも常に確認を挟む。

### 一括移動の操作状態

| 状態 | 主な操作 | 結果 |
| --- | --- | --- |
| 通常一覧 | `v` | カーソル行の選択印を切り替える。`Space`の完了切替は変えない |
| 通常一覧（選択あり） | `V` | 確認後にすべての選択印を解除する。選択中のフッターに選択件数と検索・フィルタ・折り畳みで非表示の件数を表示 |
| 通常一覧（選択あり） | `M` | 移動先Project選択へ進む。選択がなければ通知して何もしない |
| 移動先選択 | `↑`/`↓`, `Enter`, `a`, `Esc` | 移動先を選ぶか作成する。Escは一覧へ戻り、選択印を保つ |
| 移動内容確認 | `↑`/`↓`, `y`, `Esc`/`n`/`q`/`Enter` | 要約とID対応を確認して実行、または中止 |

```text
プロジェクト: デフォルト
> * #12 [ ] ブログを作る
    + #13 [ ]  記事の構成
      + #14 [ ]  下書き
  * #27 [ ] 画像を準備
...
移動選択: 3件 / 対象8件 / 非表示1件 | v:変更 M:移動 V:全解除
```

確認画面では要約を上部に固定し、移動元の選択タスクとその子孫を一覧表示して移動前ID→移動後IDを一件ずつ示す。対象件数が画面高を超えるときは確認画面内をスクロールできる。要約を確認したうえで全件の明細を任意に閲覧してから確定できる。成功後は移動元に留まり、移動行の近くへ選択を移して完了通知を出す。

## 5. CLIとプロジェクト管理

CLIはTUIを補完する操作経路とし、スクリプトで対象を明示できるようにする。プロジェクトの作成・一覧・名前変更を提供する。デフォルトプロジェクトは名前変更・削除不可。プロジェクト削除・アーカイブは初版に含めない。

通常のCLIではルートpersistent flag `--project <name>` を任意指定し、タスク操作の対象を明示する。省略時はデフォルトを対象とする。例:

```text
tque project add "ブログ"
tque project list
tque --project "ブログ" add "記事を書く"
tque --project "ブログ" ls --all --tree
tque project rename "ブログ" "技術ブログ"
tque project move --from "デフォルト" --to "ブログ" 12,27,31
tque ls --all-projects --json
```

`--project`はルートpersistent flagとし、CLIサブコマンドと引数のどちらより前でも受け付ける。TUIの起動にも適用する。空文字・重複指定・`project`管理コマンドとの併用は引数エラーとする。help/version/completionは従来どおり設定・データを読み込まない。`--all-projects`は読み取り一覧専用とし、JSONにはプロジェクトIDと表示名を含める。タスク更新コマンドとの併用は拒否する。スコープ外のIDを指定した場合は「対象プロジェクト内にタスクがない」として扱い、他プロジェクトの所属情報を表示しない。

TUIとCLIは同じプロジェクト境界・検証規則を使う。名前解決は更新ロック内で行い、操作中のrename/create競合によって別プロジェクトを変更しない。

プロジェクト名は表示用の値とし、内部参照には変更されないProjectIDを使う。名前は空でないことを検証し、同名判定は`strings.EqualFold`相当で行う。名前は正規化せず、制御文字を拒否する。既定の「デフォルト」は固定プロジェクトであり、名前付きプロジェクトには使えない。

既存タスクを分類し直すため、TUIでは`v`で複数のタスクを選び、`M`でまとめて別プロジェクトへ移す。CLIには同じ処理を行う`project move --from <name> --to <name> <id-list>`を用意する。移動元と移動先は必須で、移動先は移動元と異ならなければならない。選択対象は各タスクとその全子孫の和集合とし、祖先・子孫が重複選択された場合は一度だけ移動する。移動対象には移動先の次のIDから旧ID昇順に連番を再割当てし、InternalID、作成日、完了日時、その他の属性は維持する。選択枝の外にあるタスクとの依存関係がどちら向きでも存在する場合は操作を拒否し、先に関係を解消する。

## 6. 保存形式と整合性

- schema_versionを4へ上げる。
- ドキュメントに`projects`一覧を追加し、各タスクに必須の`project_id`を追加する。Projectは固定のID・nameを持ち、デフォルト以外のProjectIDは新規生成する。プロジェクト作成日時等の未使用メタデータは持たせない。
- 既存タスクをデフォルトプロジェクトへ割り当て、IDと親子・依存関係を維持する。
- ProjectIDと名前の重複、存在しないProjectID、デフォルトプロジェクトの欠落を読み込み時に検証する。
- 表示用タスクIDはプロジェクト内で一意にする。デフォルトプロジェクトの既存IDは保持し、名前付きプロジェクトは各々1から採番する。CLIのタスクIDは指定プロジェクト内で解釈する。
- 内部タスク同一性の`InternalID`はドキュメント全体で一意に保つ。親子・依存参照は保存時にInternalIDで結ぶ。
- 現行engineのタスク参照はint64 IDをmap keyとしているため、ProjectIDでスコープしたタスク集合を作ってから`Views`・`Select`・更新・検証・renumberを実行する。全ProjectsのフラットなTasksをそのまま現行engineへ渡さない。同じproject-local IDの衝突を避ける。
- 複数Project間の移動は唯一の横断更新とし、通常のproject-scoped Applyとは分けた専用操作にする。専用操作は移動元・移動先ProjectID、選択ID一覧、expectedRevisionを受け、ロック下の全DocumentでID・InternalID・依存関係を検証する。結果に移動前後のID対応表を含め、原子的に保存する。
- 親子関係・依存関係は同一プロジェクト内だけ許す。別プロジェクトへの参照は保存前検証で拒否する。
- ProjectIDは文字列の安定した一意値、プロジェクト名は現行タイトル同様に前後空白を除去した後で1〜200 Unicodeコードポイント、制御文字不可とする。大文字小文字の衝突判定はGoの`strings.EqualFold`とし、Unicode正規化はしない。デフォルトは固定ProjectIDと固定表示名「デフォルト」を持ち、名前変更できない。
- 親子・依存参照の保存形式は現行schema 3同様にInternalIDを使用する。表示IDはプロジェクト内のIDとしてengine処理へ渡すため、同じID値を持つタスクの異なるプロジェクト間でengineの検索・集計を混ぜない。
- schema 2/3読み込みでは既定プロジェクトをメモリ上で補い、読み込みだけで書き換えない。最初の成功した更新時にschema 4として保存する。
- ProjectIDは変更不可の内部IDとし、表示名変更でタスク所属が壊れないようにする。

### ID振り直し

renumberは選択中の一つのプロジェクト内に限定し、他プロジェクトのIDへ影響させない。全プロジェクト一覧は`project_id`とプロジェクト名を必ず表示する。

## 7. 既存データ移行

読み取り時にschema 2または3の全タスクをデフォルトプロジェクトとして扱う。読み取りだけではファイルを書き換えない。次の内容更新時にProjects一覧と各タスクのProjectIDを含むschema 4を原子的に保存する。移行前の入力ファイルを専用バックアップ（例:`tasks.schema2.backup`、`tasks.schema3.backup`）に保存し、失敗時に元データを変更しない。移行用バックアップの同名ファイルが移行元と異なる場合は既存方針に従い停止し、手動退避を案内する。旧版はschema 4を読めないこと、旧版での復旧は専用バックアップからの手動復元になることを明記する。

## 8. スコープ外

- プロジェクトをまたぐ親子・依存関係。
- 選択した枝の一部の子孫だけを移し、残りを元の枝に残す操作。選択したタスクの子孫はまとめて移動する。
- 境界をまたぐ依存関係を自動変換する操作。
- 複数プロジェクトを混ぜたTUI一覧。
- プロジェクト単位の別ファイル・保存先設定。
- 初版のプロジェクト物理削除。

## 9. 必要な検証

- schema 2/3の読み込み、デフォルト所属、読み取り専用時の非書換え、更新時移行、世代別バックアップ、障害時の原本保持。
- CLIの既定スコープと`--project`スコープ、`--all-projects`の読み取り専用一覧、スコープ外IDの扱い。
- TUI複数選択、検索で隠れた選択行の可視化、選択解除、祖先・子孫の重複整理、一括移動の確認と取消。
- 選択枝のプロジェクト移動、依存境界の拒否、移動後のID割当てと内部参照維持。
- 親子・依存関係の同一プロジェクト制約と、renumberのID・参照整合性。
- TUIの起動既定、プロジェクト選択・取消、絞り込み解除、行選択・スクロール、切替後の誤操作防止。
- 既存CLI/TUI操作がデフォルトプロジェクトで従来どおり動作すること。
