## 1. 目的と適用範囲

タイトル、親子関係、依存関係、開始日、期日、進捗を管理するGo製の単一バイナリを設計する。CLIとTUIは同じ業務ロジックと保存処理を使用する。本文、クラウド同期、複数ユーザー共有、通知、繰り返しタスクは今回の基本設計の対象に含まれない。

Windows・macOS・LinuxでCLIとTUIの両方が動作することを初版の必須要件とする。「単一バイナリ」はOS/CPUごとにCLIとTUIをまとめた実行ファイルを配布する意味であり、一つの実行ファイルを全OSで共用する意味ではない。

本書は基本設計、利用者の作業ルール、および「未確定部分をclaude codeと確定してください」という委任に基づく。第2章は確定した判断の一覧である。外部ライブラリの具体的API、採用バージョン、OS固有の保証は未検証であり、対応する実装で採用する前に一次資料と実機で確認する。

追加・具体化した動作も本書の確定仕様とする。[レビュー対象の第1版](detailed-design-reviewed-v1.md)、[レビュー原文](claude-review.md)、[共同決定に渡した草案](detailed-design-decision-draft.md)、[Claude Codeの回答](claude-decisions.md)、[指摘への評価と最終調整](review-response.md)を保持する。基本設計と差異がある箇所は本書を実装基準とする。仕様確定はコード作成・配布の実施を意味しない。

第6版までは設計・レビュー作業。第7版では利用者の実装指示に基づきアプリとスクリプトを作成し、検証を行った。外部資料・依存取得・開発用のリポジトリ外アクセスは利用者が許可済み。配布パッケージの公開やGit操作は行っていない。[実装・検証記録](implementation-status.md)に実施範囲を記録する。

## 3. 構成と責務

| パッケージ | 責務 | 禁止する依存 |
| --- | --- | --- |
| `internal/model` | 永続データ、状態定数、要求・結果の型 | CLI、TUI、ファイルI/O |
| `internal/engine` | 入力検証、タスク操作、DAG検査、日付、表示値計算 | Cobra、Bubble Tea |
| `internal/storage` | ロック、読込、保存、スキーマ検証の入口 | CLI/TUI表示 |
| `internal/config` | 設定読込・検証、保存ディレクトリの解決 | タスク更新、CLI/TUI表示 |
| `cmd` | Cobraの引数処理、engine呼出、出力、終了コード | 独自の業務ルール |
| `internal/tui` | Bubble Teaによる入力状態と描画、engine呼出 | 独自の保存処理 |
| `main.go` | コマンド起動とプロセス終了 | 業務ロジック |

engine内のServiceがRepositoryインターフェースを使用し、storageが実装する。グラフ・進捗計算は副作用のない関数に分離する。時刻はClockとして注入し、日付のテストを再現可能にする。

起動処理はconfigで解決した絶対パスをstorageへ渡す。engineとTUIは独自にホームや設定ファイルを探さず、同じRepositoryを使用する。

OS固有のロック・置換・端末処理は共通インターフェースの背後へ隔離する。GoのOS別ファイルまたはビルド制約で実装を選び、engineへWindowsのAPIやパス規則を持ち込まない。macOS/Linuxの実装をダミーやロックなしで代替しない。

概念上のインターフェース（採用ライブラリのAPIではない）:

```go
type Repository interface {
    Read(ctx context.Context) (Document, error)
    Update(ctx context.Context, expectedRevision *int64,
        mutate func(*Document) error) (Document, error)
}
```

Updateは排他ロック取得、最新データ読込、revision照合、複製データへの変更、全体検証、保存、ロック解放を一つの処理として扱う。mutate失敗時は元データもファイルも変更しない。ロック中に対話入力や描画を待たない。

## 4. データモデル

### 4.1 保存ドキュメント（Q01/Q02/Q12）

```json
{
  "schema_version": 3,
  "revision": 1,
  "tasks": [
    {
      "id": 1,
      "internal_id": "legacy-1",
      "title": "全体設計",
      "status": "todo",
      "progress": 0,
      "progress_mode": "auto",
      "created_at": "2026-10-21T00:00:00Z"
    }
  ]
}
```

未作成時の論理状態はschema_version=3、revision=0、tasks=[]。読取だけではtasks.jsonを作成しない。既存のデータディレクトリ内では読込時もlockファイルの作成を許可する（第6.1節）。IDは正のint64整数で、ドキュメント内で重複しない。schema_version 1（`next_id`を持つ0.1.0の形式）はUnsupportedSchemaとし、変換しない。

新しいIDは、ロック中に読み込んだ全タスク（完了済みを含む）のID最大値+1、タスクがなければ1とする。親子・依存・表示条件は関係しない。最大IDがint64の上限ならInvalidInputとし、保存しない。revisionの上限を超える更新もエラーにする。

revisionは0以上のint64範囲とし、expectedRevisionも同じ型で照合する。schema_versionと各必須フィールドの欠落は不正データとして扱い、ゼロ値で補完しない。

Taskは基本設計の各フィールドを保持し、progress_modeを追加する。日付は時刻なしのYYYY-MM-DD、作成・完了日時はUTCのRFC3339文字列。未設定の親、日付、完了日時は省略する。メモリ上とCLI JSONでは親・依存を表示用IDで扱う。保存境界で固定の内部IDへ変換し、保存ファイルでは `parent_internal_id` と `depends_on_internal_ids` を使う。内部依存IDは重複なく文字列順で保存する。

保存時のprogressは数値指定またはdone操作で設定する値であり、親の集計値とは区別する。集計値は保存せず、表示用TaskViewのeffective_progressに計算する。モード切替や子の追加・削除では保存進捗を書き換えない。最後の子がなくなったタスクは、保持していた保存進捗を表示する。done→undoneの後なら0となる。詳細は第4.3節を唯一の状態定義とする。

表示用IDの変更は `renumber ID NEW_ID` またはTUIの `i` で行う。変更先が使用中なら間の既存番号を1つずらし、欠番なら対象だけ変更する。全タスクを対象に番号を一括変換し、固定内部IDと保存された参照は変更しない。新規採番は引き続き表示用IDの最大値+1。表示用の親・依存番号はメモリ上で変換後に再ソートし、検証後に1回のトランザクションで保存する。TUIの選択と折り畳みは固定内部IDで新番号へ対応付ける。競合時に番号変更・削除があれば編集を中止し、入力を別タスクへ適用しない。

### 4.2 不変条件

- IDの重複、存在しない親・依存先、自己参照、循環を拒否する。
- statusはtodoまたはdone。progressは0〜100。doneなら保存progress=100、completed_atあり。todoならcompleted_atなし。
- progress_modeはautoまたはmanual。葉は保存progressを表示し、親のautoだけが集計対象。
- created_atは編集で変更しない。doneの再実行は成功扱いとし完了日時を変更しない。ただし未完了の子孫がある場合は、既にdoneでもdone操作を拒否する（Q07）。
- doneの親の下に未完了の子孫がある状態は不正データとしない。子のundone、完了済みの親への子の追加・親の変更で生じ得る（Q07）。
- start_dateとdue_dateが両方あればstart_date <= due_dateとする。
- 不正な保存データを空データ扱いしない。未知のスキーマや未知フィールドを読み捨てて上書きしない。

schema 2は読込時に旧IDから `legacy-<id>` の固定内部IDを割り当てる。原本は読込だけでは変更せず、初回変更保存時に `tasks.schema2.backup` と通常バックアップを作成してschema 3を保存する。同名の移行バックアップが別内容なら停止する。新規タスクの内部IDは暗号学的乱数16バイトの16進文字列とし、空値・重複を拒否する。schema 1は移行しない。

### 4.3 進捗・状態の組合せ（Q02/Q03/Q06/Q07）

| status | 子の有無 | mode | 保存progress | effective_progress |
| --- | --- | --- | --- | --- |
| todo | なし | auto/manual | 0〜100を保持 | 保存progress |
| todo | あり | manual | 0〜100を保持 | 保存progress |
| todo | あり | auto | 0〜100を保持（集計には不使用） | 直下の子のeffective_progress平均を切り捨て |
| done | なし/あり | auto/manual | 必ず100 | 必ず100 |

| 操作 | 保存progress | mode | status・完了日時 |
| --- | --- | --- | --- |
| add（-p省略またはauto） | 0 | auto | todo・日時なし |
| add -p N | N | manual | todo・日時なし |
| edit -p N | N。doneでN<100なら拒否 | manual | 変更しない |
| edit -p auto | 保持 | auto | 変更しない |
| done | 100 | auto | done・初回のみ完了日時設定。未完了の子孫があれば拒否（既にdoneでも同じ） |
| undone | 0。既にtodoなら保持 | 保持 | todo・完了日時削除。既にtodoなら無変更成功 |
| 子の追加・削除・移動 | 保持 | 保持 | 変更しない |

葉のauto指定も許可し、保存値を失わず将来親になった場合の集計方法を選択できる。数値指定済みの葉に子を追加するとmanualは維持される。固定継続をCLI/TUIの行の`[manual]`表示で明示する。自動集計への変更は-p autoまたはTUIのpから行う。完了前の進捗を履歴として復元する機能は持たない。

## 5. 入力と業務ロジック

### 5.1 入力規則（Q11）

- titleは不正なUTF-8を拒否し、前後の空白を除去して1〜200コードポイント（Goのrune単位）とする。空文字、改行、タブ、ESC等の制御文字を拒否する。日本語・絵文字を保持し、Unicode正規化による書換えはしない。表示時にも端末制御シーケンスを出力しない。TUIでも同じ検証を行い、貼付けを黙って切り詰めずエラーを表示する。
- IDは正の10進整数。0、負数、小数、範囲外を拒否する。
- 日付は厳密なYYYY-MM-DD、today、+Nd（Nは0〜36500の整数）。有効範囲は0001-01-01〜9999-12-31。ローカル日付を操作受付時に一度取得し、暦日加算する。無効日、範囲外、オーバーフローを拒否する。日付は着手の強制制限に使わない。
- editの未指定は維持、noneはparent/dep/start/dueの解除。titleの文字列noneは通常のタイトル。progress解除はQ02のautoを用いる。
- --depはカンマ区切りと繰返し指定を受け付け、editでは集合全体の置換。例: `--dep 2,3 --dep 4`。noneとIDの併用は拒否する。基本設計の`<id...>`はこの構文に具体化する。
- editで変更フラグがない場合は使用方法エラー。複数フラグの更新は全件成功または全件失敗とする。

### 5.2 操作

| 操作 | 更新内容 | 主な検証 |
| --- | --- | --- |
| Add | 既存タスクの最大ID+1（なければ1）を割当、todo、作成日時設定 | タイトル、日付、親、依存、進捗 |
| Edit | 指定された属性だけ置換 | 変更後のドキュメント全体 |
| Done | status=done、progress=100、progress_mode=auto、完了日時設定 | 存在、全子孫がdone（Q07）、Q04の方針 |
| Undone | status=todo、progress=0、完了日時削除 | Q06の方針 |
| Remove | 対象または子孫集合を削除 | cascade指定、集合外からの依存参照 |

Addで-pに数値を指定した場合はmanual、auto指定または省略時はautoとする。-p 100だけではdoneにしない。doneのタスクへの100未満の進捗指定は拒否し、先にundoneを要求する。親や依存関係、タイトル、日付はdoneでも変更できる。

自動進捗はdoneを100として優先し、todoのmanualは保存値、todoのautoで子ありは直下の子のeffective_progress平均の切り捨て、葉は保存値とする。子変更後は祖先を再計算する。親statusの自動変更は行わない。

blockedは依存先に一つでもtodoがあるとき成立する（Q14）。依存先なしの場合はfalse。blocked_byには未完了依存IDのみを昇順で列挙し、親や開始日からは推論しない。自分のstatusがdoneでも同じ判定を使い、CLI/TUIとも`(blocked by #2, #3)`を表示する。JSONも同じblocked/blocked_byを返す。--blockedは一覧のstatusフィルタを適用した後、この判定で絞り込む。新たなactionable_blockedフィールドは追加しない。

### 5.3 グラフ

ID→TaskとParentID→子ID列を構築する。参照存在を確認後、白・灰・黒の訪問状態によるDFSで閉路と経路を検出する。親子は子→親の包含関係、依存はタスク→先行必須タスクとして別々に検査する。エラーには`#1 -(parent)-> #3 -(parent)-> #1`または`#1 -(dep)-> #3 -(dep)-> #1`のように関係種別を付ける。

| 例 | Q08での扱い |
| --- | --- |
| 親が子に依存 | 許可。子の完了まで親にblocked警告 |
| 子が親に依存 | 許可。親の完了まで子にblocked警告。blockedは警告のみ（Q04）のため子を先に完了でき、その後に親を完了できる（Q07） |
| 兄弟間・別の枝の子孫間の依存 | 依存グラフが非循環なら許可 |
| 親と子が互いに依存 | 依存グラフの閉路として拒否 |
| 親子グラフ単独では非循環、依存グラフ単独でも非循環だが結合時のみ循環 | 拒否しない。包含を先行条件として扱わないため |

深い階層でも処理可能なよう、実装は明示スタックを用いる。検査・進捗計算はO(V+E)、順序確定のソートはO(V log V)を目安とする。削除集合は親子だけを辿り、依存先を巻き込んで削除しない。

## 6. ストレージと並行実行

保存先は第6.4節で解決したデータディレクトリ内の`tasks.json`。既定値は`~/.tque/tasks.json`。同じディレクトリに`lock`、`tasks.json.tmp`、`tasks.json.backup`、`tasks.json.backup.tmp`を置き、設定ファイルの場所とは区別する。ホーム解決失敗はエラーとする。テストはホーム・設定・データ用の一時ディレクトリを注入し、実ユーザーデータを使わない。

### 6.1 排他処理

解決済みデータディレクトリの`lock`を対象にOSのファイルロックを使用する。既定の配置は`~/.tque/lock`。ファイルの存在そのものをロックとせず、異常終了後に手動削除を要求しない方式を選ぶ。ロックファイルは解放時に削除しない。Windows、macOS、Linuxそれぞれの実装または採用ライブラリを技術選定する。ネットワーク共有上の利用保証は対象外とする。

読込・更新とも同じ排他ロックを使用する。共有ロックは初期版に導入しない。読込では、データディレクトリが存在しないことを確認した場合にその時点の空状態を返す。後続の作成操作より前の読込として扱い、その後の更新は必ずロック下で再読込する。存在確認時の権限エラー等を「存在しない」と解釈しない。指定したデータディレクトリが通常ファイル等の場合、lockの作成・オープンができない場合はStorageFailureを返す。

ディレクトリが存在する場合はlockを必要に応じて作成し、排他ロック取得後にtasks.jsonを調べる。本体が未作成なら空状態を返すが、本体は作成しない。更新時のみデータディレクトリを作成する。ロック取得に失敗した読込は、ロックなしで処理を続行しない。

待機はcontextで中断可能にし、上限5秒でタイムアウトを返す。OSの非ブロッキング取得と中断可能な待機を組み合わせ、ロック競合時は最大50ms間隔で再試行する設計とする。contextの期限が短ければそちらを優先し、競合以外のエラーは直ちに返す。採用APIがこの動作を実現できるかは技術検証する。全プロセスが同じロック規約に従うことを前提とし、外部エディタや同期ソフトによる書換えは保護できない。初期版の保証対象はローカル保存とし、保存先変更用の公開フラグ・環境変数は追加しない。

### 6.2 更新手順

1. ロックを取得し、最新JSONを読んで形式・不変条件を検証する。
2. expectedRevision指定時は一致確認。不一致なら変更せず競合エラー。
3. ドキュメントを複製し、変更と全体検証を行う。
4. 実変更があればrevisionを1増加。無変更なら保存しない。
5. 本体が存在する場合は第6.6節の保存前バックアップを完了する。
6. 同じディレクトリの`tasks.json.tmp`へ完全なJSONを書き、Sync、Closeを行う。
7. OS別の置換処理でtasks.jsonを置換する。
8. 必要な永続化処理を行い、結果を返してロックを解放する。

固定tmp名はロック所有者だけが操作する。候補データの検証とJSON生成を完了してから、tmpを作成または切り詰めて全量を書き込む。残留tmpは自動復元に使わない。本体が破損している場合はtmpにも触れず停止する。書込・Sync・Close失敗後は置換を行わず、tmpの削除を試みる。削除失敗は副次エラーとして通知し、本来のエラーを保持する。置換結果が不明ならtmpも自動削除せず、再読込と確認に回す。本体を削除してからリネームする方式は使用しない。

初期版では置換を自動再試行せず、失敗を返す。将来再試行を追加する場合は「本体が未変更と判定できる一時的エラー」をOS別に特定し、回数・待機上限・中断処理を定めてから導入する。未検証のエラーを一括で再試行しない。

基本設計はos.Renameによるアトミック置換を要求しているが、全対象OSでの上書き・アトミック性・電源断耐性は未検証。Windowsを含むOSごとのAPI契約を確認し、必要なら専用実装に置き換える。原子的な可視性と電源断後の永続性は別の受入項目とする。

置換前の失敗、または置換APIの契約上本体が未変更と確認できる失敗はStorageFailureとする。置換の成否自体を判別できない場合と置換後の永続化確認失敗はCommitUncertainとし、Addを自動再試行しない。ロック解放失敗は保存の成否とは別に通知する。壊れたJSONは元ファイルを保持して停止し、初期化・切捨てをしない。

| OS別の技術確認項目 | 現在の状態 | 完了条件 |
| --- | --- | --- |
| 初回作成と既存ファイル置換のAPI | 第7版で選定・実装。Windows/Linuxの試験済み、macOS実行未確認 | 採用根拠と結果はimplementation-status.md |
| 可視性と永続化の保証範囲 | Sync/Close/置換後処理を実装、障害注入を検証。電源断未検証 | 電源断耐性を推定で保証しない |
| 排他ロック・中断・異常終了後の解放 | Windows/Linuxで複数プロセス・中断・異常終了後の再取得を確認 | macOS実行確認が残る |
| 制限付きハンドル・読取専用属性・残留tmp | Windows制限付きハンドル・破損時の残留tmp保持を確認。読取専用属性等の追加受入は未実施 | データ消失なし、失敗段階と通知を個別確認 |

この表はWindows・macOS・Linuxそれぞれについて検証し、OS・ファイルシステム・使用APIと結果を記録する。一つのOSでの成功をほかのOSの確認済み根拠にしない。macOS/Linuxでも置換後の永続化、権限エラー、異常終了時のロック解放を確認する。技術検証用の小規模実装は、製品仕様確定と区別して進められる。

### 6.3 TUIとCLIの同時利用

TUIは一覧のrevisionと編集開始時のrevisionを保持する。保存は最新データに対し要求を適用するが、revisionが異なる場合は拒否する。再読込後も入力案を保持して利用者に再操作を求める。無関係なタスクの変更でも競合になる保守的な設計とする。

rキーで再読込する。初期版では常時監視を行わず、起動時・操作成功時・競合時・明示再読込時に表示を更新する。

### 6.4 設定ファイルと保存先の解決

設定ファイルはユーザーのホームを基準にした`~/.tque/config.json`とする。データ保存先を変えても設定ファイルの場所は変えない。形式はUTF-8のJSONオブジェクトで、先頭のUTF-8 BOMは許容する。初期版の設定項目は`data_dir`だけとし、コメント・末尾カンマ・重複キー・未知キー・後続の別JSON値は拒否する。

3 OS共通でこの場所を使用し、macOSのLibraryやLinuxのXDG設定ディレクトリへ自動的に切り替えない。ホームは実行OSのユーザーホーム解決機能から取得し、C:/Users、/Users、/homeなどをコードに埋め込まない。

```json
{
  "data_dir": "D:/tque-data"
}
```

この例では`D:/tque-data/tasks.json`、`D:/tque-data/lock`、`D:/tque-data/tasks.json.tmp`を使用する。設定例は[config.example.json](config.example.json)として提供する。アプリは設定ファイルを自動生成・上書きせず、利用者が作成・編集する。

| 設定・パス | 動作 |
| --- | --- |
| config.jsonが存在しない、またはdata_dir省略（{}） | ホーム配下の.tqueを使用 |
| data_dirが空文字、空白のみ、null、文字列以外 | ConfigError。既定値へ戻さない |
| 絶対パス（例: D:/tque-data） | 指定したディレクトリを使用 |
| 相対パス（例: data） | 設定ファイルの親ディレクトリ基準。例では~/.tque/data |
| ~、~/...（Windowsでは~\\...も） | 現ユーザーのホームへ展開。~user形式は拒否 |
| %VAR%や$VAR等 | 環境変数として展開しない。特殊なテンプレート構文を持たない |
| Windowsでのドライブ相対パス（D:data）・ドライブなしルート相対パス（\\data） | 実行場所に依存するため拒否 |
| WindowsでのUNCパス | 絶対パスとして解決できるが、ネットワーク共有の排他・永続化は保証対象外 |

Windowsの区切りは/と\\を受け付ける。JSON内で\\を書く場合はエスケープが必要なため、設定例では/を用いる。パスは空白だけかの検査を除いて勝手にtrimせず、内部の空白・日本語を保持する。絶対化と`.`/`..`の整理を行い、制御文字・NULを含む値は拒否する。

macOS/Linuxの区切りは/とし、\\をWindowsの区切りとして変換しない。絶対パスはOS固有なので、Windows用のD:/...を他OSへそのまま持ち込まない。OS間で共用しやすい設定例は`{"data_dir":"~/tque-data"}`とする。[config.example.json](config.example.json)はWindowsの絶対パス例、[config.portable.example.json](config.portable.example.json)は3 OS共通のホーム相対例として提供する。

tasks.jsonの構造は3 OS共通とし、ドキュメント内に保存先やOS固有のパスを記録しない。全プロセス停止後に別OSへコピーして同じタスクを読み込めることを検証する。config.jsonの絶対パスは移行先に合わせて指定する。Unicodeのタイトルやファイル名をOS間移行時に勝手に正規化しない。

起動時に一度だけ設定を読み、解決した保存先をプロセスの終了まで固定する。TUIのrはタスクデータだけを再読込し、設定変更の適用には再起動を必要とする。CLIは各起動で設定を読み直す。CLIフラグや環境変数による保存先上書き、設定を変更するサブコマンドは初期版には追加しない。

設定が不正、読取権限がない、設定ファイルがディレクトリである等の場合は、設定パスと理由を示すConfigError（終了コード1）で停止する。設定が存在しない場合以外のI/Oエラーを未設定扱いしない。help/versionは設定・データを読み込まず利用可能とする。設定の読込・検証が終わるまで、データディレクトリやlockを作成しない。

指定先が存在しない場合、読込は空状態を返し、最初の更新時に必要な親ディレクトリと保存先を作成する。作成・書込に失敗した場合は指定先を示して停止し、既定の保存先へ代替保存しない。TUIのヘッダーには解決済みデータパスを表示し、幅が不足する場合は省略表示する。CLIの正常出力・JSONの形式は変更せず、保存関連エラーにデータパスを含める。

### 6.5 保存先を変更する際のデータの扱い

設定変更はデータの選択先を切り替える操作であり、既存タスクを自動移動・複製・統合しない。新しい保存先にtasks.jsonがあれば検証してそのデータを使い、なければ新規の空データとして扱う。

既存データを引き継ぐ場合の手順は、(1)すべてのtqueプロセスを終了、(2)元のtasks.jsonをバックアップ、(3)内容全体を新しい保存先へコピーし既存ファイルを無断で上書きしない、(4)config.jsonのdata_dirを変更、(5)再起動してls --allで確認、の順とする。revisionを含む保存ドキュメント全体を保持する。lockや残留tmpは移行せず、元データは確認が済むまで残す。

異なる保存先は別のタスク集合として扱う。設定の変更中に起動しているTUIは元の保存先を使用し続けるため、保存先の切替・移行は全プロセス終了後に行う。同じ保存先を使うプロセスはその保存先のlockを共有し、設定ファイル側のlockで代用しない。

### 6.6 保存前バックアップ

実変更を保存する直前に、ロック下で読込・検証済みの本体を同じデータディレクトリの`tasks.json.backup`へ1世代保存する。最初の作成、無変更成功、検証・revision照合失敗ではバックアップを書き換えない。壊れた本体で正常なバックアップを上書きしない。

元の本体の全バイトを`tasks.json.backup.tmp`へ書き、Sync・Close・OS別置換・必要な永続化を終えてから本体の保存へ進む。バックアップ失敗時は本体を更新せず、対象パスと理由を通知する。バックアップの置換結果が不明な場合も本体は未更新であることを明示して停止する。残留backup.tmpは自動復元に使わない。

本体とバックアップの2ファイルを一括で原子的に変更できるとは保証しない。バックアップ完了後に本体保存が失敗した場合、backupと本体は同じ保存前データになり得る。成功した通常更新の後はbackupが直前のデータとなる。バックアップは操作履歴やUndoではなく、同じドライブの障害に対する外部バックアップでもない。

復元は全プロセス終了後に手動で行う。現在の本体・backup・残留tmpを別名で退避してから、検証できるbackupを本体へコピーする。バックアップ時点より後の変更は復元されない。正常に読み出せる退避本体のrevisionを確認し、復元後のrevisionは両者の大きい値+1とする。上限超過は復元作業を停止する。復元専用コマンドや自動復元は初版に追加しない。

## 7. CLI詳細

基本設計のadd/edit/done/undone/rm/lsに加え、表示用IDを変更するrenumber（第4.1節）とシェル補完のcompletion（第7.2節）を実装対象とする。引数なしまたは--tuiでTUIを起動し、サブコマンドと--tuiの併用は拒否する。TUI起動時に対話端末がなければ明確なエラーを返す。

| 項目 | 仕様 |
| --- | --- |
| 正常出力 | stdoutへ結果。失敗説明はstderr |
| 終了コード | 0成功、1業務・保存・競合エラー、2引数エラー、3保存結果不明（CommitUncertain） |
| ls | 既定はQ09の対象をID昇順で表示。検索・条件・ソートは第7.2節 |
| --tree | 親子順で表示。フィルタ対象の祖先を文脈行として残し、対象外であることを表示 |
| --blocked | todoかつblocked。--all併用時はdoneの関係上の警告も対象 |
| --json | 表示用の行をJSON配列で出力。色と通常メッセージを混ぜない |
| --tree --json | 拒否。階層はparent_idから復元可能 |
| 空一覧 | 通常表示は対象なし、JSONは[]、終了コード0 |
| --help/--version、completion | 設定・保存領域へアクセスせず出力 |

JSON行はTaskの各属性とeffective_progress、blocked、blocked_byを持ち、保存ドキュメントとは別の公開形式とする。--jsonでは文脈用祖先を混入しない。フラグの正当性は保存処理を呼ぶ前に確認する。

### 7.1 入力と出力の契約

| 入力 | add | edit |
| --- | --- | --- |
| -p 0〜100 / auto | 第4.3節の初期値を設定 | 第4.3節の遷移 |
| --parent/--dep/--start/--due none | 拒否。未設定なら省略 | 該当属性を解除 |
| titleとしてnone | 通常のタイトル | 通常のタイトル |
| 未指定の属性 | 初期値（関係・日付なし） | 保持 |

日付表示は年を含むYYYY-MM-DDに統一し、保存値と同じ意味にする。通常一覧は`ID [ ]/[x] TITLE [manual] [########.. 80%] START -> DUE (blocked by #N)`の要素順とする。manual以外はモード表示を省略、進捗バーは10桁で塗る数をeffective_progress/10の切捨て、空きは`.`とする。日付なしなら日付欄を省略、片側だけなら`START ->`または`-> DUE`。依存警告なしなら末尾を省略する。ツリーはIDの前に枝を付け、文脈用祖先には`[context]`を付ける。階層内の兄弟は選択中のソート条件で並べ、既定はID昇順。

追加は`[+] Created task #ID: TITLE`、編集は`[*] Updated task #ID`、完了は`[x] Completed task #ID`、未完了へ戻す操作は`[ ] Reopened task #ID`、削除は`[-] Removed N task(s): #ID, ...`。無変更成功は`[=] Unchanged task #ID`とし、revisionは増加させない。エラーはstderrに型名・対象・理由を表示する。

CLI出力はUTF-8、初期版は色なしとする。TUIは色と文字を併用するが、NO_COLORが非空なら色を無効化する。古いコードページのコンソールへの自動変換はしない。Windows・macOS・Linuxの実端末で表示・入力・終了後の端末復帰を確認する。

| JSON属性 | 型・未設定時の規則 |
| --- | --- |
| id | 正のint64範囲のJSON整数 |
| title / status / progress_mode | 文字列。statusとmodeは定義済みの列挙値 |
| progress / effective_progress | 0〜100の整数 |
| parent_id | 整数。未設定なら省略 |
| depends_on / blocked_by | 昇順・重複なし整数配列。空でも[]を出力 |
| start_date / due_date | YYYY-MM-DD。未設定なら省略 |
| created_at / completed_at | UTCのRFC3339。completed_atはtodoなら省略 |
| blocked | boolean。第5.2節の判定 |

nullは出力しない。JSON配列内のタスクも第7.2節のソート条件に従い、既定はID昇順。保存側の省略可能なdepends_onとは出力規則を区別する。整数の精度を保てるJSON処理系を前提とし、CLIがIDを浮動小数点数へ変換しない。

### 7.2 検索・表示条件・シェル補完

| CLI指定 | 定義 |
| --- | --- |
| ls --search TEXT | タイトルの部分一致。大文字小文字を区別せず、語順は保持。空文字は検索なし。曖昧一致・正規表現は初版に含めない |
| ls --due-today | todoかつ期日がローカルの今日以前。「今日まで」なので期限超過も含む |
| ls --overdue | todoかつ期日が今日より前 |
| ls --ready | todoかつ未完了依存なし、開始日なしまたは開始日が今日以前 |
| ls --sort id / due / name | idはID昇順。dueは期日の早い順、日付なしは最後。同じ日付ならID昇順。nameはタイトルのUnicodeコードポイント順、同じタイトルならID昇順（読み仮名による並べ替えはしない） |
| completion powershell / bash / zsh / fish | 指定シェルの補完スクリプトをstdoutへ出力する |

検索・条件はANDで結合する。--allは通常のtodo限定を外すが、--due-today/--overdue/--ready自体のtodo条件は外さない。--blockedと--readyの併用は矛盾する指定として引数エラーにする。期日なしは日付フィルタに一致しない。

今日の基準日は1回の評価につき一度取得する。CLIは受付時、TUIは条件変更・再読込時およびローカル日付変更時に再評価する。readyは表示上の条件であり、操作禁止ルールを追加するものではない。

ツリーは一致タスクとその祖先を残す。祖先の表示値は全子タスクから算出し、絞り込み後の子だけで進捗を再計算しない。--sort dueでも親子をばらさず、各階層の兄弟をそのタスク自身の期日で並べる。

補完対象はコマンド・フラグと、sort、progressのauto、解除可能なフラグのnone等の固定候補。初版はID補完のために保存データへアクセスしない。`--root`の値も補完しない。生成したスクリプトの導入方法をREADMEに記載し、プロファイルやシェル設定は自動編集しない。

### 7.3 起点タスクの指定（Q21）

`--root VALUE`はルートコマンド（TUI起動）と`ls`のローカルフラグとする。ほかのサブコマンドとの併用は引数エラー（終了コード2）。help/version/completionは従来どおり設定・データを読み込まない。

| 項目 | 規則 |
| --- | --- |
| 値の検証 | 前後空白を除去。空文字・制御文字を含む値は引数エラー |
| 照合 | 値が第5.1節のIDとして解釈できればそのIDのタスク、およびタイトルが`strings.EqualFold`で一致するタスクを候補にする。同じタスクは1件として扱い、完了済みも含める。部分一致は使わない。並びはID昇順 |
| 候補0件 | NotFound（終了コード1）。TUIは起動しない |
| 候補1件 | その起点で表示する |
| 候補2件以上 | TUIは起点選択画面（第8.6節）。`ls`はInvalidInput（終了コード1）とし、候補を`#ID 祖先 > … > タイトル`でエラーに列挙する。stdoutには出力しない |
| `ls`の表示範囲 | 起点と子孫。検索・条件・並びはこの範囲に適用する。`--tree`では起点を深さ0として先頭に表示し、文脈行は起点で止める。JSONの形式は変えない |

照合は読込で取得したDocumentに対して行い、利用者の選択をロック保持中に待たない。

## 8. TUI詳細

一覧、全文詳細、属性入力、検索入力、削除確認、保存中、ヘルプ、エラー表示を状態として扱う。選択は行番号ではなくタスクIDで保持し、削除時は近傍行へ移す。ウィンドウサイズ変更時は表示幅とスクロール範囲を再計算する。

| 操作 | 状態遷移と処理 |
| --- | --- |
| j/k・上下 | 一覧の選択移動。末尾と先頭で停止 |
| PageUp/PageDown | 一覧の表示行数単位で選択移動 |
| J/K | 画面上の選択位置を固定して一覧を下/上へスクロールし、その行に来たタスクを選択。空行は飛ばし、先頭・末尾では停止。入力中は文字 |
| 左/右 | 折り畳み・展開および親子への移動。第8.2節 |
| / | タイトル検索を開始。入力中に一致行を更新 |
| f | 全件→未完了→今日まで→期限超過→着手可能→全件と条件を切替 |
| o | ID順→期日順→名前順→ID順と切替 |
| ? | 現在の状態の操作ヘルプを表示（属性・検索入力中は文字として入力） |
| Space | 対象のdone/undone要求 |
| +/- | 表示進捗±10を0〜100へ制限してmanual指定。doneではどちらも無変更とし、先にundoneするよう通知 |
| a/A | タイトル入力。Aは選択タスクを親として保持 |
| e | 現在タイトルを初期値に編集 |
| s/d | 現在日付を初期値に入力。空欄で解除 |
| l | 現在の依存ID列を初期値に入力。空欄で解除 |
| x/Delete | 対象と削除件数を表示。子ありなら子孫削除を明示して確認 |
| Enter/Esc | 入力確定・取消。取消時は保存しない |
| q/Ctrl+C | 一覧では終了。入力中のqは文字、Ctrl+Cは未確定入力を破棄して終了 |
| r | 一覧を再読込 |
| p | 進捗入力。0〜100またはautoを指定 |
| i | 表示用IDの変更入力。第4.1節。非表示のタスクも番号変更の対象 |

削除確認は既定を取消とし、明示的な肯定入力だけで実行する。子孫集合外からの依存があればQ05に従って拒否し、参照元IDを表示する。

確定操作ごとに保存し、成功後に表示を更新する。終了時の全件上書きはしない。保存中は二重更新を受け付けず、終了要求は保存結果が判明してから処理する。入出力はBubble Teaの非同期コマンドから行い、結果メッセージで状態を更新する。

日本語・結合文字・絵文字はバイト数で切らず、端末表示幅を考慮する。幅不足ではタイトルを省略し、極小画面ではサイズ不足表示を行う。blockedは色だけでなく文字でも示す。入力中のj/k等は編集文字として扱う。エラー後も入力を保持して修正できるようにする。

### 8.1 状態遷移の補足

- Space、+/-はキー受付時の一覧revisionを送る。入力欄と削除確認は開始時のrevisionを保持する。
- 保存中は「保存中」を表示し、追加の更新キーは破棄して後から再生しない。リサイズは処理し、Ctrl+Cによる終了要求は保留する。qは保存中には終了要求として扱わず破棄する。
- 保存成功後は返却されたDocumentで一覧を更新する。表示再読込の失敗を、保存失敗と混同しない。
- 競合時は再読込し、入力案を表示して再確定を求める。新しいrevisionで自動再送しない。対象が消えていれば編集を中止し、入力案を通知欄に残す。
- 保存中の終了要求は成功後に終了する。失敗・結果不明の場合は終了保留を解除し、エラーを表示して利用者の再操作を待つ。
- 追加成功時は新タスクを選択して表示位置を合わせる。削除後は旧行位置に来た次の行、なければ前の行を選択する。空一覧では選択なし。
- 選択なしで対象を必要とするキーは「対象タスクがありません」と通知する。a、r、q、/、f、o、?は使用できる。
- 親の変更は初期版ではCLIのedit --parentで行う。TUIに新たな親変更キーは追加しない。
- 削除確認は`y`で確定、`n`/Esc/Enterで取消。確認中のqは取消、Ctrl+Cは未確定の削除を破棄して終了する。
- TUIの日付・モード・進捗・警告の意味と各値の表記は第7.1節に合わせる。CLIの行全体の配置とは分け、TUIは第8.3節の領域に配置する。未確定の列配分・省略方式は第8.4節で管理する。pの初期値はautoならauto、manualなら保存進捗とする。

### 8.2 検索・折り畳み・操作案内

検索は第7.2節と同じ判定を使う。Enterで検索条件を保持して一覧に戻り、検索入力中のEscは入力開始前の条件に戻す。一覧でEscを押すと検索条件だけを解除し、fで選んだ条件は維持する。検索中のj/k等は文字入力であり行操作として扱わない。

折り畳み状態はタスクIDごとにプロセス内だけで保持し、データを保存しない。起動時は子を持つすべてのタスクを折り畳んだ状態とし、ルートタスクだけを表示する。親を展開すると直下の子を表示し、孫以下の親は折り畳んだままとする。この初期化は起動時だけ行い、rによる再読込では利用者の開閉状態を保持して折り畳み直さない。起動後に子を持つようになったタスク（追加・再読込で親になったもの）は展開した状態で扱う。左は展開中の行を折り畳み、それ以外なら表示されている親へ移動する。右は折り畳みを開き、既に開いていれば最初の表示子へ移動する。該当する親・子がない場合は無変更。依存編集のlキーは維持し、左右移動へ流用しない。

検索中または条件が全件以外のときは、一致行までの経路を自動展開する。絞り込み表示中は折り畳み変更を行わず、左右は表示上の親・最初の子への移動だけにする。通常表示の折り畳み状態は保持し、条件解除後に復元する。検索・条件変更で選択が見えなくなれば先頭の一致行、なければ選択なしとする。

追加成功時は新タスクの祖先を展開する。新タスクが条件に合わない場合は「追加済み・現在の条件では非表示」と通知し、条件を勝手に変更しない。これは第8.1節の新タスク選択の例外である。折り畳みで選択子孫を隠す操作では選択を折り畳んだ親へ移す。

ヘルプは移動・追加編集・検索表示・終了のカテゴリに分け、上下でスクロールし?/Escで元の状態へ戻る。属性入力・検索入力中は?を文字として扱い、下部にEnter確定・Esc取消を表示する。削除確認中は?で確認操作のヘルプを開き、戻っても削除を実行しない。保存中は保存待機と終了保留の説明を下部に表示する。

下部には状態に応じた主要操作だけを常時表示し、全キーを詰め込まない。全件が空なら「a: タスクを追加」、一致ゼロなら「Esc: 検索解除 / f: 表示条件切替」を表示する。検索文字列・表示条件・ソート順・一致件数をヘッダーに表示し、絞り込み中であることを明確にする。一致件数は条件に合うタスク数であり、文脈用祖先を含めない。これらはQ19の操作案内として採用し、別途検討する配色・列幅・詳細ペイン等の画面意匠とは分ける。

### 8.3 採用する画面構成（Q20）

利用者の「再検討に関しては、一旦保留し、推奨で進める」という指示に基づき、次の構成を採用する。レビューの改善案すべてを承認した意味ではない。

| 領域 | 役割 |
| --- | --- |
| ヘッダー | 保存先、検索文字列、表示条件、ソート順、一致件数 |
| ツリー一覧 | 階層、選択、完了状態、タイトル、進捗、期日、依存警告を比較する中心領域 |
| 下部詳細 | 選択タスクのタイトル、状態、進捗モード、開始日・期日、親、依存関係を確認。属性編集・削除確認時には対象を明示した入力・確認領域として使用 |
| 独立した通知欄 | 保存中、保存結果、エラー、競合等を表示。下部詳細とは別に保持し、選択移動だけで重要な通知や保持した入力案を失わない |
| 操作案内 | 現在の状態で使う主要キー。?は引き続き操作ヘルプ |
| 全文詳細画面 | 一覧や下部詳細で省略したタイトル・依存関係を全文確認する読み取り専用画面。表示しきれない情報をスクロールして閲覧 |

通常は一覧の横幅を維持する下部詳細方式とする。右側詳細への分割、カレンダー、常設サイドバーは初版に追加しない。標準配置は次のとおり。寸法を検証した描画図ではない。

```text
ヘッダー：保存先／検索／表示条件／並び／一致件数
ツリー一覧：階層・タスク・状態・進捗・期日・依存警告
────────────────────────────────────────
下部詳細（編集・確認時は入力領域）
────────────────────────────────────────
独立した通知欄：保存結果・エラー・競合等
状態に応じた操作案内

全文詳細画面：省略情報を読み取り専用で全文閲覧
```

保存処理は第6・9章に従う。全文閲覧でデータを書き換えず、保存結果不明を成功または未保存と断定しない。手動進捗は一覧でも`[manual]`を維持する。ここでの通知欄はアプリ内の操作結果表示であり、第1章で対象外とした期限通知等の機能追加ではない。

### 8.4 保留事項と適用範囲

第6版で保留した事項を次に記録する。実装開始後、利用者はEnterで全文詳細・Escで戻る、検索入力中の左右は文字カーソル移動、80x24の描画を基準に画面幅を調整する推奨案を承認した。この範囲は第8.5節に具体化し、それ以外の再検討は保留を維持する。

| 保留項目 | 保留中の扱い |
| --- | --- |
| 保存結果不明後の再送方式 | 元のrevisionで再送する新方式は採用せず、既存の再読込・結果確認方針を維持 |
| manualの短縮記号 | `*`等への変更を行わず、既存の`[manual]`を維持 |
| 通知の詳細閲覧キー・保持解除条件 | ?はヘルプに維持。独立した通知欄と選択移動で失わない原則のみ確定 |
| 全文詳細の起動・終了キー | 第7版で解決。一覧のEnterで開き、Escで戻る |
| 列幅・最小端末サイズ・階層省略・開始日の一覧配置 | 第7版で80x24を基準に実装・描画試験。具体的な実装値を第8.5節へ記録。実端末での追加調整は検証結果に基づいて行う |
| Unicode文字の追加制限 | Cfの一律拒否等を追加せず、既存の入力検証と日本語・絵文字保持方針を維持 |
| 具体色・完了行の減光 | 特定のANSI灰色を確定しない。色なしの識別を保ち、明暗背景で確認 |

第6版の構成採用だけで個別の改善案を一括承認したとは扱わない。第7版で実装した操作の具体化は次節に記録し、保存結果不明の再送方式やUnicode追加制限等は既存方針を維持する。

レビュー原文と比較は [画面レビューの比較](screen-review-summary.md) を参照。画面案第1版はレビュー対象として保存し、本節が現在の採用範囲を示す。

### 8.5 初期実装の操作・描画

- 一覧のEnterで読み取り専用の全文詳細を開き、Escで戻る。上下/j/k・PageUp/PageDownで全文をスクロールする。ヘルプも同じスクロール方式。
- 検索・属性入力中の左右は文字カーソル移動。Space・j/k・?は文字入力とし、入力中に一覧の完了・階層操作を行わない。結合文字を分断しない単位で左右移動・削除する。
- 最小画面は40セル×10行。未満ではサイズ不足を表示して更新を受け付けず、q/Ctrl+Cで終了できる。80×24を標準確認サイズとし、40×10、60×14、120×30も描画試験した。
- 幅80未満、またはタイトル幅が不足する場合は進捗バーを省略して数値を残す。幅60未満では期日を下部・全文詳細へ移す。開始日は下部・全文詳細で表示する。
- `[manual]`を維持し、`[context]`と依存待ちの`!dep`を一覧で識別する。依存待ちのID列は詳細の`(blocked by #N)`で確認する。深い階層ではインデントを制限し、省略を`..`で示す。開閉印はASCIIのv/>を用いる。
- 高さ20以上の下部詳細は4行、14〜19は1行、それ未満は常設詳細を省略。入力・削除確認中は最低2行を確保する。選択は`>`、色が有効なら反転も併用。固定の灰色や独自テーマは追加しない。
- 通知は次の操作結果等で置き換えるが、選択移動だけでは消さない。既存の?ヘルプと全文詳細の末尾にも最新通知・保存先を表示し、省略された文を読めるようにする。通知履歴機能は追加しない。
- 文脈行も選択・操作可能で、下部に条件不一致を表示する。操作で選択タスクが条件から外れた場合は近傍行へ移す。検索条件変更時は従来どおり先頭の一致行を選ぶ。
- 保存中はリサイズと終了要求を処理し、それ以外のキーを後から再生しない。保存結果不明時は更新を止め、再読込による確認へ進める。ヘルプによる通知全文の閲覧と終了は可能。

これらは描画と状態遷移を確認した初期実装であり、3 OSの全端末・IME・フォントの受入完了を意味しない。

### 8.6 起点表示（Q21）

- 起点選択画面: 候補ごとにID、状態、祖先からの経路、表示進捗を示す。経路が幅に収まらない場合は先頭側の祖先を`..`で省略し、候補自身のタイトルを残す。上下/j/k・PageUp/PageDownで選択、Enterで開く、Escで起点なしの全体表示、q/Ctrl+Cで終了。データを変更せず、rは受け付けない。
- 起点は固定内部IDで保持し、番号変更に追随する。別の親の下へ移されても表示を続ける。再読込・保存後に起点がなければ全体表示へ戻し、`起点 #N は削除されたため全体表示に切り替えました`と通知する。TUI内で起点を変更・解除するキーは設けない。
- 表示範囲は起点と子孫。起点を深さ0として先頭に表示し、通常のタスクとして操作できる。深さ・インデント・階層色は起点からの相対深さ。ツリーの開始は「表示行に親がない行」とし、起点表示では空行で区切らない。進捗・依存警告・ID列幅は文書全体から計算する。
- 起動時の折り畳み（第8.2節）のうち、起点だけを展開する。
- `a`は起点の子として追加する。入力欄のラベルは`#N の子を追加（起点）`。起点の行の左キーは折り畳みだけを行い、範囲外の親へ選択を移さない。
- ヘッダー1行目は`tque  起点: 祖先 > … > タイトル (#N)  保存先: PATH`。幅が不足する場合は保存先を先に省略し、次に先頭側の祖先を`..`で省略する。起点のタイトルとIDを残す。`?`ヘルプには起点の全経路を表示する。

## 9. エラー設計

config/engine/storageからは型付きエラーを返し、UIが表示する。例: ConfigError、InvalidInput、NotFound、CycleDetected、ReferencedTask、RevisionConflict、LockTimeout、CorruptData、UnsupportedSchema、StorageFailure、CommitUncertain。

エラーには操作、対象ID、原因となる参照ID等を含める。成功と確認できない保存を成功表示しない。保存エラー時の次操作は再読込を基本とする。無限リトライや破損データの自動修復は行わない。

JSON構文エラーと不変条件違反はCorruptDataの理由で区別し、検出箇所・対象IDを示す。未知のスキーマはUnsupportedSchemaとする。これらではlsを含むデータ操作を停止し、壊れたデータ用の一覧・修復コマンドは初期版に追加しない。help/versionは利用できる。

手動復旧は、(1)利用者がtqueを終了、(2)tasks.jsonと残留tmpを別名で退避、(3)既知の正常なバックアップを復元、または退避コピーを基に指摘された不整合を修正、(4)lsで再検証、の順とする。未知のスキーマ番号を書き換えて読み込ませない。アプリが自動でファイルを削除・初期化することはない。

自動作成したtasks.json.backupから復元する場合も、第6.6節の退避・カウンター確認を行う。ヘルプとシェル補完は本体や設定が壊れていても利用できる。

ロック解放等の副次エラーはCLIではstderr、TUIでは通知欄へ出す。保存完了が確認できている場合は「保存済み・ロック解放失敗」と明示し、未保存と誤認させない。CLIは保存済みの操作結果と追加時のIDをstdoutへ表示し、終了コード1を返すが自動再試行を促さない。永続ログファイルは初期版に設けない。

### 10.1 性能の目標と計測

初期版の想定規模は10,000タスク、親子の深さ1,000、依存辺20,000。これは検証対象であり、超過しただけでデータを拒否する上限ではない。次の値は共同設計で設定した目標であり、実測値ではない。

| 項目 | 1,000件 | 10,000件 |
| --- | --- | --- |
| ls（起動から出力完了） | 200ms以内 | 1秒以内 |
| add/edit（ロック・同期含む） | 300ms以内 | 1.5秒以内 |
| TUI起動から初回描画 | 300ms以内 | 1秒以内 |
| TUIカーソル移動（保存なし） | 50ms以内 | 50ms以内 |

Windows・macOS・LinuxそれぞれのローカルSSD環境、releaseビルドで計測する。1回ウォームアップ後に各30回以上測定し、p95（昇順でceil(0.95×標本数)番目）を記録する。ロック競合や故意の保存障害を入れない条件とし、更新試験は各回同じ初期データから開始する。lsはUTF-8の出力完了までをファイルへのリダイレクトで測り、端末の描画速度と分離する。TUIは端末・画面サイズを固定し、実端末で描画計測方法も記録する。

CPU、メモリ、OS、Go版、端末、データ生成条件、階層深さ、依存辺数を併記し、値を異なる環境への保証にしない。深さ1,000でスタックがあふれないことを確認する。未達時は原因を記録して改善または仕様改訂を判断し、記録なしに目標値だけを下げない。

## 11. ビルド・配布・ライセンス

利用者の指示に基づき、実装時には最低限次を用意する。

- `scripts/build-release.ps1`: Windowsからのリリースビルド入口。OS/CPUを指定可能にし、失敗時は非0終了。
- `scripts/build-release.sh`: macOS/Linuxからのリリースビルド入口。同じVERSION、対象、出力規則を使用する。
- `scripts/build-installer.ps1`: Windows用Inno Setupインストーラー作成。-Sign指定時に環境変数CODESIGN_CERTを利用してアプリ実行ファイル、インストーラー、アンインストーラーへ署名する。
- `installer/tque.iss`: Windowsのインストール対象、アンインストール、署名処理の構成。
- `scripts/package-release.sh`: macOS/Linux用アーカイブ作成。対象OS/CPU、実行権限、ライセンス、チェックサムを確認する。
- `docs/version-update-checklist.md`: バージョン変更時に更新する実ファイル一覧。

CODESIGN_CERTの値の形式、署名ツール、タイムスタンプ先、既存スクリプトとの互換性は未確認。値をログへ出さず、署名失敗時に未署名の成功成果物として扱わない。アンインストーラー署名の具体的方法はInno Setupの公式仕様を確認して実装する。

このInno SetupとCODESIGN_CERTによる署名手順はWindows用とする。macOSの署名・公証やLinuxの配布物署名へ同じ設定を流用できるとは仮定しない。macOSの配布時の署名・公証条件、資格情報、実行時のOSによる検証は別途調査し、ダウンロードした成果物を通常の導入手順で起動できることを配布受入で確認する。署名済み・公証済みの表記は実際の検証結果に限る。

### 11.1 配布とバージョン管理の決定

- 初版からWindows・macOS・Linuxをサポート・配布対象にする。下表を実装・検証対象とし、実行未確認の成果物を対応済みとして公開しない。
- 初回バージョンは0.1.0。実装時にリポジトリ直下のVERSIONを唯一の値の定義元とし、バイナリとInno Setupへビルド時に注入する。具体的な注入方法はビルドスクリプト作成時に検証する。
- docs/version-update-checklist.mdにはVERSIONの更新、リリースノート（CHANGELOG.md）の追記、バージョンを記載した利用文書の確認、生成物への反映確認を記載する。実装後に実ファイル一覧を確定し、値を複数ファイルで手動同期させない。
- Windowsはユーザー単位のインストールとし、管理者権限を必須としない。インストール先は%LOCALAPPDATA%/Programs/tque。
- WindowsではユーザーのPATHへインストール先を重複なく追加する。既存項目の有無と追加実績を記録し、アンインストール時は自ら追加した項目だけを削除する。既存PATH全体の古い値で上書きしない。更新インストールでも追加実績を引き継ぐ。
- macOS/LinuxはOS/CPU別のtar.gzで実行ファイルとライセンス・利用手順を提供する。利用者がPATHの通った場所へ配置する方式とし、ユーザー単位の配置例は~/.local/bin/tque。シェル設定を自動編集せず、PATH追加が必要なら手順を示す。初版でHomebrew、deb、rpmへの登録は必須にしない。
- アンインストールで~/.tqueの設定・既定データ、および指定先のデータを削除しない。インストーラーは利用者のconfig.jsonを生成・上書きしない。

### 11.2 Go・モジュール・ライセンスの決定

moduleは`tque`とし、初版ではgo installによる公開取得を提供しない。公開リポジトリの所有権を確認できた段階で、公開取得を必要とする場合にモジュールパス変更を検討する。未確認のGitHub URLを設定しない。

本体はMITを採用する。著作権者の正式表記は、実装時にリポジトリの権利者情報を確認してLICENSEへ記入する。呼称「レモン」から法的名義を推定しない。これはライセンス選択の未決事項ではなく配布前の記載情報の確認である。Cobra、Bubble Tea、Lip Glossと推移依存のバージョン・Go要件・ライセンスを採用前に確認し、必要な著作権表示を同梱する。

Go 1.22への互換性維持は要件としない。実装開始時点の安定版を確認してビルド用ツールチェーンを選び、採用版をtoolchainとリリース記録へ残す。go.modのgo行は自コードの言語機能と採用依存の要求をともに満たす値にする。低いgo行を書くだけでその版の動作保証とはせず、保証する版は実際の検証記録で示す。

2026-10-21のローカル確認では`go version`は`go1.27.0 windows/amd64`、ISCC.exeはPATHから検出できた。これは最新安定版の外部確認やアプリのビルド成功を意味しない。signtool.exeはPATHからは検出できておらず、未導入とは断定しない。署名ツールの場所・CODESIGN_CERTの形式・タイムスタンプ先は署名実装前に確認する。
