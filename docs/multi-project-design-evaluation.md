# 複数プロジェクト設計案: レビュー評価

日付: 2026-10-24  
対象: [設計案](multi-project-design-proposal.md)  
外部レビュー: [Claude Codeレビュー記録](multi-project-claude-review.md)

## 評価の結論

Claude Codeが示した高重大度の懸念は、現行のID採番・renumber・厳格JSON・移行方式と照らして妥当。既存の詳細設計には現行実装と異なる箇所もあるため、機能設計を正式仕様へ入れる前に基準を明示する。

改訂提案では次の方針を推す。

1. **表示用IDはプロジェクト内で一意**にする。デフォルト側の既存IDを保持し、名前付きプロジェクトは独立した採番とrenumberを持つ。InternalIDは文書全体で一意とし、保存上の親子・依存参照を維持する。
2. **CLI一覧は既定でデフォルトだけ**を表示し、全件を必要とする場合は明示的な`--all-projects`を追加する。全件JSONにはProjectIDと名前を含める。名前付きProjectの追加後、CLIの出力集合は明示スコープに従うため、既存スクリプトの変化を互換性上の注意として文書化する。
3. **既存タスクの分類用にルートと全子孫の移動**を提供する。移動先で衝突しないProject内IDを割り当て、InternalID・属性・履歴を保つ。依存参照が移動境界を越える場合は黙って切らず、移動を拒否する。
4. **初版ではアーカイブを設けない。** 作成・一覧・名前変更に絞り、削除操作も含めない。アーカイブ状態と復元の曖昧さを持ち込まずに済む。
5. **schema 2/3からschema 4への読み込み移行を定義**し、移行専用の`tasks.schema2.backup`/`tasks.schema3.backup`を用意する。移行用バックアップと通常の1世代バックアップの役割を分ける。

1〜3は目的（プロジェクト境界と既存ツリーの整理）を満たす設計上の推奨であり、永続データ形式・ID表記・CLI出力の変更を伴う。採用前に利用者の判断が必要。

## 指摘ごとの評価

| 指摘 | 評価 | 設計案への対応 |
| --- | --- | --- |
| H1 全体IDとrenumberの干渉 | 妥当。現行renumberは範囲内のIDを動かし、非表示プロジェクトに影響し得る | Project内IDへ変更し、renumberを同一Projectに限定 |
| H2 全体採番が既定表示を変える | 妥当。採番とID列幅は全ドキュメントを見ている | Project内の最大IDで採番・列幅を計算 |
| H3 移行バックアップ/schema 2経路不足 | 妥当。schema 2は現行実装でまだ読み込み対象 | schema 2/3双方の移行経路、専用バックアップ、ダウングレード手順を設計へ追加 |
| H4 既存タスクを移動できない | 妥当。既存タスクを名前付きProjectへ整理できない案では利用目的を満たしにくい | ルートと全子孫の一括移動を提案へ追加 |
| H5 CLI一覧・IDエラーの曖昧さ | 妥当。現行CLIにはProjectスコープがないため追加時に契約を決める必要 | デフォルトを既定スコープ、全件取得は明示、Project識別付きJSONを提案 |
| H6 厳格JSONフィールド不足 | 妥当。未知・欠落フィールドの検証に失敗すると読み込み全体が停止する | Project一覧、必須project_id、ProjectID固定、名前制約を提案 |
| M1 アーカイブ挙動 | 妥当 | 初版からアーカイブを外す |
| M2 名前解決競合 | 妥当 | 更新ロック内でProjectIDを解決する。TUIはProjectIDを保持する |
| M3 TUI遷移不足 | 妥当 | 保存中等の切替禁止、入力中の`P`、filter解除・sort保持を明記 |
| M4 `--project`境界 | 妥当 | ルートpersistent flag、help等での非読込、TUIにも適用する案 |
| M5 詳細設計と実装差 | 要確認として扱う。レビュー指摘の一部は現行ソースでも確認できた | 現行実装を実挙動の根拠としつつ、詳細設計の該当箇所を別途整合させる必要を明記 |

## TUI一括移動案への再レビュー評価

Claude Codeの再レビューでは、初回案のTUI操作をさらに具体化するよう求められた。次の点は設計案に反映した。

| 指摘 | 評価と対応 |
| --- | --- |
| 選択印のID・Project範囲 | 表示IDの変更や重複を避けるためInternalIDで持つ。選択印は現在の移動元Projectだけに限定し、印が残る間のProject切替は拒否する案とした |
| 検索・折り畳み・幅 | hidden件数は検索・filter・折り畳みで隠れた行を対象とし、viewport外の行は含めない。印と暗黙に含む子孫を別表示し、カーソル表示セルを再利用する。選択中はフッターを短縮する |
| 競合・保存結果不明 | 確認時revisionを要求へ渡す。競合時は再読込して再確認し、自動再送しない。CommitUncertain後はInternalIDを元・先Projectで照合し、印を解除する |
| 初回移動先なし | 移動先画面からProjectを作成可能にする。Project作成は移動とは別の保存として明示する |
| 確認画面の操作量 | 固定要約とスクロール可能な全件ID対応表を使う。末尾まで読まないと確定できない強制ゲートにはしない |
| 成功後の画面 | 移動元に残る。連続して別の枝を別Projectへ整理しやすく、検索・filterも維持する |
| engineの単一ID前提 | Project間移動を専用の横断更新にし、移動元/先、ID一覧、expectedRevisionとID対応表を扱う案を追加 |

この再レビュー対象案では、Project切替を拒否する理由とTUI表示は提案へ追加したが、最小画面での実際の描画適合は設計・実装検証の対象として残る。

## 参考リポジトリとの照合

- PMのREADMEはproject属性と`--project`フィルタを説明する。tqueの明示スコープCLIの参考になるが、一覧フィルタと厳密な操作境界は同一ではない。
- RonDOのREADMEは単一のローカルSQLiteデータベースを説明する。単一ストアの参考にはなるが、今回確認した資料にプロジェクト分割の根拠はない。
- ruskのREADMEはDB形式・保存場所の選択、複数同時実行、バックアップ等を説明する。tqueのプロジェクトは独立保存先としてではなく、現行単一文書内の分割として扱う。

参照資料は公開READMEである。各リポジトリの実装上の詳細を網羅的に確認したものではない。

## 未確定項目

- プロジェクト内IDを採用するか。レビュー推奨と評価者推奨は採用だが、既存JSON/CLIのID意味を変えるため承認待ち。
- `--all-projects`のCLI出力・JSON拡張を追加するか。
- 既存ツリーの移動機能を初版に含めるか。InternalID・履歴維持の設計と受け入れ条件の承認が必要。
- schema 2を直接schema 4へ移行するか。提案では対応を維持。
- `--project X`指定時にTUIをXで開くか。提案では開く。
- 移動時に境界をまたぐ依存関係がある場合、拒否するか、確認のうえ依存を解除するか。提案では拒否。
- `V`で全選択印を解除する前の確認、空一覧時のキー処理、大文字キー表記。
- 詳細設計書の親変更・複数選択対象外という既存方針を改訂し、実装挙動との差（undone・親完了制約・進捗モード等）をどの基準で解消するか。

これらを正式な詳細設計へ反映する前に、利用者が選択する必要がある。レビュー評価と設計案は仕様承認を意味しない。
